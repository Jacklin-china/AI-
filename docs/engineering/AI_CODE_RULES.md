# Kantoku AI Coding 强制工程规范

生效范围：以后所有 AI 对 Kantoku 源码、测试、配置、脚本及工程文档的修改。建立日期：2026-10-05。

本规范补充根目录 `AGENTS.md`、[产品原则](../product/product-principles.md)及[工程手册](README.md)。用户对当前任务的明确授权、范围和冻结要求优先；遇到文档与实际实现冲突，记录冲突，不自行扩大任务。

架构基线见[架构审计报告](../architecture/audit-report.md)，暂不能迁移的既有实现见[架构例外清单](../architecture/exceptions.md)。例外必须绑定文件、兼容原因、冻结范围和退出条件，不能成为新代码的模板。本文件建立规则，不表示 CI 已经执行全部规则。现有结构检查的缺口必须在独立治理任务中补齐。

## 1. 修改前的必备证据

修改任何文件前，按顺序完成：

1. 依次完整阅读适用的 `AGENTS.md`、本规范、产品原则、工程手册；查看架构例外清单及相关审计条目。
2. 查看 Git 分支、工作区及暂存区，区分已提交实现、用户未提交改动和临时验收文件。
3. 搜索现有 Service、API、组件、Skill、存储和调用方，包括动态入口及 Skill manifest。
4. 明确问题属于 Core、Domain、Capability、Provider/Adapter 或 UI；画出受影响的调用链。
5. 提出最小修改位置、兼容约束及验证方法，再动手修改。

新功能或新增文件必须先回答：

- 能否复用现有能力？不能复用的具体契约差异是什么？
- 为什么必须新增文件，而不能扩展现有文件？
- 为什么放在这个层级？它依赖谁、被谁调用？
- 是否改变状态、数据、接口、费用、审批或默认执行路径？

这些回答必须基于文件和调用证据。名字相似不等于职责相同；搜索不到静态引用也不等于可以删除。

## 2. One Core / One Orchestrator

必须复用既有执行、记录及能力机制：

- Run、Workflow、Node、Runtime Event 和执行状态使用现有 Core Runtime。
- 产物使用现有 Core Artifact；领域可以保存业务索引和不可变修订，但不能建立独立产物系统。
- 预算、提交认领、账单及对账使用现有 Core Budget 和账本。
- Skill 使用现有 SkillLoader、SkillRegistry；领域知识正文由现有上下文链路加载。
- Domain 编写业务节点和流程定义，不能另造执行引擎、调度器或恢复系统。

禁止建立 Comic Agent、Commerce Agent、第二套 Runtime / Artifact / Budget / Workflow / Registry。禁止通过 `NewSkillManager`、`PromptBuilder2` 等名称规避复用，禁止 `xxx_new`、`xxx_old`、`xxx_backup`、`xxx_final`、`xxx_v2` 平行实现。历史版本交给 Git。

现有 Coordinator、LLM 工具循环、GraphRuntime 和 TaskRunner 的职责必须先区分。Domain Coordinator 可以表达阶段和业务门禁，通用调度、事件、恢复、取消及运行生命周期不得再次复制。审计已发现的旧例外不能成为继续扩展例外的依据；治理须逐步复用现有机制并保留兼容调用。

## 3. 层级职责与依赖规则

| 层级 | 负责 | 禁止 |
| --- | --- | --- |
| Core | 通用执行、产物、事件、审批、预算、Skill 机制 | Comic/Commerce/Ozon/SKU 规则，具体模型协议及业务生产决策 |
| Domain | 业务实体、业务门禁、领域上下文、节点和流程定义 | 直接调用模型 SDK/HTTP API，实例化具体 Provider，复制执行引擎 |
| Capability | 可复用 AI 请求、能力结果、幂等与预算编排 | 依赖某个领域的页面、实体或业务审批策略 |
| Provider/Adapter | 外部服务协议、请求转换、响应转换、供应商错误 | 业务流转、用户审批、项目状态或工作流决策 |
| UI/Shell | 呈现、输入验证、API 边界、依赖组装 | 复制 Domain 流程、以浏览器状态替代服务端版本和权限 |
| Config | 配置、验证、通用错误及日志基础设施 | 导入业务服务并触发业务执行 |

标准能力调用：`Domain → Capability 接口 → Provider/Adapter`。领域通过接口获得能力；Shell 在组装入口注入具体实现。Commerce 等外部平台集成可以使用已有 Domain Port 与 Adapter；Port 的业务契约留在 Domain，具体协议留在 Adapter。

禁止 Comic 直接引用 Commerce 实现，反之亦然。共享需求应复用 Core 或已有通用 Capability，不能从另一个 Domain 借用内部函数。

当前供应商实现实际分布在 `tools/`、`adapters/` 和 `capabilities/video/`；当前共享文本出口在 `core/llm.py`。这是迁移债务，不要求普通修复任务立即移动目录，也不允许据此新建第二套供应商系统。类型注解或供应商错误类型引用与实际发送请求要分别检查。

## 4. Prompt、Skill 和事实来源

Comic 完整镜头 Prompt 复用 `domains/comic/prompts.py` 的现有 Compiler、修订及 Core PROMPT Artifact。首页、旧 Studio/CLI 的契约先保持兼容；合并入口必须有调用方清单和迁移方案。

必须明确保存输入版本、Brief/资产依据、Director 决策、Skill 方法证据、模型请求及人工修改来源。Skill 已加载或存在 hash，只能证明输入来源，不能证明某一输出字段的因果来源。

模型补充的外貌、服装、摄影或风格是创作选择；不得标成用户事实或资产事实。人工编辑和重新编译追加修订，不覆盖历史，不继承旧内容指纹的确认。

本轮已验收的 Comic 默认路径是：导演人工确认 → 分镜/Shot → 完整 Prompt → 用户复制到外部模型 → 上传外部图片。内部生图兼容代码是 future capability，不得默认接入或以普通重试按钮启用。首页、Commerce、Task Center 主逻辑不能随 Comic 任务顺手修改。

## 5. 状态和并发规则

同一实体的同一状态必须有一个服务端定义。Run/Node 复用 `ExecutionStatus`；前端使用对应 API 契约，不自行重新解释终态。

执行状态、领域审核状态、媒体状态、Provider 结果和账单状态属于不同对象，必须显式映射，不得强制合成一个枚举：

- `pending` 是尚未开始；`waiting` 是已有运行等待外部条件。
- Provider `unknown` 表示结果或账单未决，不等同明确失败。
- Prompt 已生成、图片已上传、Shot 已审核是三种不同事实。
- 单个异步任务必须绑定所属 Conversation / Project / Shot / Run / 请求版本；导航不消费全局媒体 Loading。

状态变化须核对预期版本，拒绝并发静默覆盖。新状态必须说明入口、出口、恢复规则、API 投影及历史兼容。迁移方案未获确认时，不直接改旧枚举和旧数据。

## 6. 费用、重试及维护脚本

所有付费调用复用现有预算和提交认领机制。相同请求不得并发重复提交；未知账单只能查询或对账，不能通过重试、释放预算或修改状态绕过安全边界。

缺少供应商任务 ID，不构成供应商未接单或零费用的证据。只有明确失败证据及合法账本转换才允许释放；未报告实际费用保留未知，不能用 `None or 0` 冒充零费用。

既有业务费用策略、工程真实模型验收预算、导演人工确认是不同授权。付费实测依工程手册单独确认预算和凭据，使用隔离库；不擅自增加产品费用确认步骤。

维护脚本必须满足：

- 导入不执行数据库或网络写操作；执行入口受 `main` guard 保护。
- 默认只读预览，显示精确筛选条件、数量及影响；写操作需要明确执行参数和授权。
- 修改账单或业务数据前有备份、迁移/恢复方案及逐条证据。
- 限定环境、目标路径、请求和业务范围；禁止无条件批量改写 unknown 账单。
- 写入复用公开服务、合法状态迁移和事务，记录操作者、原因、证据及关联 ID。

不得执行不明归属的一次性脚本来验证架构。不得删除用户数据、清空数据库、删除历史或覆盖生产数据。

`scripts/archive/` 仅保存不可运行的审计证据，不是可加载脚本目录；不得执行、动态导入、扫描执行或重新启用 `.disabled` 文件。恢复危险逻辑须另行确认范围及安全验收，不能以历史文件存在为理由释放未知账单。

## 7. 日志和错误

复用 `config/observability.py`、日志上下文及现有 Runtime Event。错误边界应提供下列结构化信息：

| 字段 | 要求 |
| --- | --- |
| `trace_id`、`error_id` | 能从公开错误定位同一次异常 |
| `run_id`、`task_id` | 有关联时必填；不适用时明确为空及原因，禁止伪造 ID |
| `module`、`error_type`、`error_kind` | 区分错误位置、原异常类型及恢复分类 |
| `reason` | 脱敏后仍能定位根因的具体说明 |
| `request_id`、`provider_request_id` | 区分应用请求和供应商请求 |
| `project_id`、`shot_id`、`provider`、`model` | 相关能力操作必须关联 |

保留脱敏异常链和堆栈，不得只写“失败，请查看日志”。禁止裸异常吞掉、业务异常 `except: pass`，禁止以日志写入失败为理由再次调用付费模型。正常 CLI 输出、队列空轮询及用户中断可以保留，但业务错误仍需进入统一错误边界。

API Key、Authorization、Cookie、密码及私有思维链不得写入日志、Trace、文档或测试证据。Prompt 正文的记录遵守既有隐私策略；优先记录版本、长度、hash 和有界脱敏信息。

## 8. 测试、Fake 与 future capability

离线测试默认禁止真实外部调用，使用隔离数据库和路径；撤销替身前等待后台 Worker 结束。真实验收与离线测试明确区分，估算费用与供应商实扣明确区分。

Fake/Mock 结果必须保留来源标记，不能被升级为真实 IMAGE / VIDEO / Commerce 交付；真实内容接口不得依靠文件存在就判断真实性。future capability 必须说明默认关闭、允许入口、责任人或待确认责任归属、启用前验收条件。

测试应验证业务契约、错误与并发边界，不能只检查源码拼写或镜像实现。未调用代码的删除需要静态引用、路由、动态导入、manifest、测试及构建证据；未证实安全时仅列候选。

禁止新依赖，除非先说明必要性、现有替代能力和移除影响。禁止为一个局部功能引入另一套框架。

## 9. 文件、打包及交付

不提交密钥、本地配置、数据库、日志、上传/生成媒体、缓存、虚拟环境、node_modules 或验收副本。运行数据不进入 Git，也不进入项目交付压缩包；清理打包清单不等于允许删除本地用户数据。

`src/kantoku/shells/web/` 是后端提供的必要静态构建交付物，不是另一套前端源码。更新时须对应同一份 `frontend/src` 构建，不手工改压缩 bundle，不因“生成文件”而清空它。

不得覆盖他人的未提交改动或暂存区。标准启动方式保持 `python -m kantoku serve` 和 `frontend/` 的 `npm run dev`，不依赖隐藏步骤。

验证按影响范围执行：结构检查、相关测试；涉及前端时构建和类型检查；涉及运行入口时检查启动；涉及数据时检查迁移和历史兼容。文档审计不启动业务或模型，不宣称旧测试结果是本轮重跑结果。

## 10. 每次提交的必填说明

提交说明或审阅记录必须包含：

```text
修改目的：
归属层级及复用依据：
影响范围 / 默认路径变化：
新增文件（无则写无）及理由：
删除文件（无则写无）及安全证据：
数据 / 状态 / 接口 / 费用 / 审批变化：
测试命令、结果及未验证项：
是否改变架构；若改变，说明兼容及迁移方案：
新增依赖（无则写无）：
人工验收结果及已知限制：
```

分模块任务必须遵守：修改 → 测试 → 人工验收 → Git commit → 下一模块。当前模块未验收，不进入下一模块。提交和向外部仓库推送须符合用户已有授权范围，不使用强制推送。

本次审计后的治理工作必须先确认审计报告中的修复顺序及范围；本规范不授权自动重构、删除或改变现有测试。

## 11. 规则执行的现状与下一步

现有 `scripts/check_structure.py` 继续作为唯一结构检查入口。治理 Module 0 仅接入 AGENTS/工程手册的必读链接和例外清单，不新增第二套 linter，不修改 guard 或 CI。

已接入修改前阅读入口。待确认的治理任务：将规则接入提交检查；增强既有检查的相对导入解析、跨 Domain 引用、具体 Provider 调用及例外清单；给规则补充正反例；接入实际使用的提交/CI 流程。文档规则、机器检查及人工审阅必须分别说明覆盖程度，不能以 `Structure guard: PASS` 声称架构全部合规。

运行文件改动同时遵守[Runtime Storage 规范](runtime-policy.md)，禁止绕过 RuntimeManager 或 DatabaseManager。
