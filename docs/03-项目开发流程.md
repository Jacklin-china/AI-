## 0 · 三句话定位

1. **卖什么**：给 AI 漫剧小团队/个人承制者做「副导演 Agent」——它不承诺一键生成爆款，专门把**分镜、角色与场景约束、候选图质检、定向返工、预算和交付复盘**做稳定。
2. **为什么有人付钱**：客户买的不是 Agent 概念，而是**更高的一次可用率、更少的返工、更可预测的交付成本**；软件先作为自己的内部生产工具，用真实订单证明后再考虑产品化。
3. **怎么算成**：W5 跑通一条可收费的最小闭环，W6 做第一次影子交付，W9 完成至少 1 次真实/自营交付并算清单位经济。**不能同时改善质量、工时或成本中的至少两项，就停止加功能。**

## 1 · 产品定位与范围

### 1.1 把痛点改写成可验证的问题

本项目只优化自己能控制的生产变量，不把播放量和爆款运气伪装成软件能力：

| 痛点 | 可控问题 | 必须记录的指标 | Agent 的动作 |
|---|---|---|---|
| 画面稳定性差 | 角色/服装/场景约束在跨镜头时丢失 | 首次可用率、连续性失败率、人工通过率 | 固化角色与场景卡；只给当前镜相关上下文；记录 prompt 版本与参考素材 |
| 废片率高 | 无差别多抽卡，失败原因不结构化 | 废片率、平均每镜生成次数、返工原因 Top 3 | 一镜先出一个候选；先质检再定向重做；禁止自动付费重做 |
| 算力成本暴涨 | 批量调用前没有预算与单镜上限 | 单可用镜头成本、单集 API 成本、未知账单数 | 项目/集/镜三级预算；reserve→调用→settle；超限阻断 |
| 盈利模式脆弱 | 只记 API 钱，不记人工与返工 | 单集贡献毛利、有效时薪、准时交付率、复购 | 每单填 §8.2；按结果报价；复盘低毛利步骤 |

> “一次可用”指无需再次付费生成、只需轻微后期即可进入成片的镜头。口径必须固定，不能为了让数据好看临时改变。

### 1.2 三层范围（先活下来，再增强）

| 层级 | 功能 | 商业作用 | 哪周 | 是否允许跳过 |
|---|---|---|---|---|
| **P0 可收费闭环** | 分镜生成 + 数据契约 | 减少拆镜机械劳动，给后续步骤稳定输入 | W2 | 否 |
| **P0 可收费闭环** | 角色/场景约束 + prompt 版本化 | 降低跨镜头漂移，失败可追溯 | W3 | 否 |
| **P0 可收费闭环** | 生图编排 + 三级预算台账 | 控制每镜和每单最坏成本 | W4 | 否；API 可用假实现替代 |
| **P0 可收费闭环** | VLM 预筛 + 人工终审 + 定向返工队列 | 降低人工筛图和盲目重抽卡 | W5 | 评分项可砍，硬缺陷判定保留 |
| **P0 商业证据** | 影子交付 + 单位经济报告 | 证明不是“省了时间却亏了钱” | W6、W9 | 否；接不到单就自做 |
| **P1 可靠性** | 记忆/检索、checkpoint、HITL | 只有试单证明确实需要时才补 | W6–W7 | 允许按 §5 决策降级 |
| **P2 集成/作品集** | MCP、可选交互外壳 | 方便外部调用，不直接决定首单盈利 | W8、W10 | 允许跳过 |

**范围判定规则**：新需求必须先在 §8.2 的真实工时记录中出现，且满足“高频、昂贵、可重复”至少两项，才允许进入 P0/P1。没有记录的想法只进 Future Work，不写代码。

### 1.3 明确不做（红线，写了就删）

| 不做 | 原因 |
|---|---|
| 模型微调（LoRA / SFT / DPO / RLHF） | 那是另一个岗位，JD 里和 Agent 应用开发分开招 |
| **引入 Agent 框架作为运行时依赖**（LangChain / AutoGen / CrewAI） | 手写内核是差异化；但**允许手写状态机并做概念对标**（见 §7.1） |
| 向量数据库集群（Milvus / Qdrant） | 单机单用户，sqlite-vec 足够 |
| ComfyUI 本地部署 | 当前 10 周不做；云 API 故障时切云供应商或用假实现验证编排 |
| 多 Agent 编排 | 单 Agent + 工具已够，编排是范围陷阱 |
| 底座 Open-LLM-VTuber 作前置依赖 | v2.0 全量重写中，降级为 W10 可选外壳 |
| 自动剪辑/配音/发布/投流/收益预测 | 当前闭环只做到“稳定生产可用画面 + 交付报告”；全链路会让范围失控 |
| 自动触发付费重做 | VLM 可能误判；任何新增付费必须由人确认 |

**Future Work 进入条件**：只有在 W9 单位经济通过后，才评估图生视频适配器、时序一致性质检、自动剪辑与平台发布；仍须逐项经过预算控制器，不得回填进当前 10 周主线。

### 1.4 成功标准（按商业价值排序）

- [ ] **交付成立**：用 Agent 完成至少 1 集真实或自营交付，客户/目标用户接受，不以“生成出来了”冒充可交付。
- [ ] **单位经济成立**：收入（自营则填可验证的目标报价）减去 API、外包、退款/补偿等直接成本为正；同时填写人工工时和有效时薪，不混入虚假的“零人工成本”。
- [ ] **效率成立**：相对同口径手工基线，首次可用率、总工时、单可用镜头成本三项中至少两项改善，且客户接受率不下降。
- [ ] **风险可控**：成本台账误差 ≤5%；发生过一次超限拒绝；超时后产生的未知账单能对账，不重复扣费重试。
- [ ] **质量可回归**：分镜 / 一致性 / 质检评测集齐全；prompt、模型或阈值变更必须留版本并回归。
- [ ] **可复现**：同一项目能从记录恢复“用了哪个模型、prompt 版本、参考素材、为何返工”，README 能演示完整证据链。

MCP 调用、向量检索、VTuber 外壳属于加分证据，不再作为“能赚钱”的硬性成功条件。

## 2 · 系统全景（先读这个，再看周计划）

**场景**：接了一单，剧本《雨夜便利店》第 3 集，800 字，要出 20 镜静帧。当前 v1 的交付边界止于“稳定可用的静帧包 + 分镜/prompt + 质检和成本报告”，不假装已经覆盖完整视频制作。

### Step -1 · 建订单基线（贯穿 W1–W9）

先在 §8.2 记录交付范围、报价/目标报价、手工基线、验收口径和预算上限。**没有基线不允许声称提效，没有验收口径不允许批量付费生成。**

### Step 0 · 建项目与角色卡（W3）

录入 2 张角色卡，存 SQLite `persona` 表：

```
小雨：17岁便利店店员，黑色齐耳短发，红色围裙，圆脸，眼神困倦
老陈：50岁常客，灰色夹克，秃顶，戴老花镜
```

**为什么先有它**：后面每一镜的生图 prompt 都从这里取特征词——这是"人物一致性"的根。人物、服装、画风、场景分别设为可复用约束；单镜不得随意改全局约束。

### Step 1 · 分镜生成（W2）— **K2 Function Calling 完整链路**

```
你的话 + 工具说明书 → LLM
LLM 决定："我要调 generate_storyboard，参数是这段剧本"
你的代码解析 JSON → 执行函数 → 结果回喂 LLM
LLM 用人话回你："拆好了，20 镜，预计 3 分 20 秒"
```

```json
{"shot_no": 7, "desc": "小雨在货架前整理泡面，抬头看向门口",
 "dialogue": "欢迎光临……咦？", "camera": "中景，固定机位，轻微推近",
 "duration_s": 8, "characters": ["小雨"]}
```

### Step 2 · 上下文裁剪 + 拼 prompt（W3）— **K3 Context Engineering**

笨办法是把 20 镜 + 全部角色卡一股脑塞进去（贵且角色特征互相污染）。正确做法：生成第 7 镜时**只喂**①第 7 镜描述 ②小雨与当前场景的约束（老陈不进窗口）③前 2 镜的连续性摘要。

```
裁剪前 3200 token → 裁剪后 640 token（省 80%）
1girl, black bob hair, red apron, round face, sleepy eyes,
convenience store shelf, arranging instant noodles, …
```

每次生成同时记录 `prompt_version`、模型、尺寸、参考素材 ID，以及供应商支持时的 seed；不支持 seed 时明确记为不可复现，不伪造确定性。

> **上下文工程的价值**：不是堆更长的提示词，而是把“必须稳定的约束”和“本镜允许变化的内容”分开。

### Step 3 · 出图 + 扣钱（W4）— **K6 成本治理**

```
reserve(预估费用) → 带幂等键提交 → 查询任务状态 → settle(实际费用)
台账写一行：时间 / 集数 / 镜号 / 预估 / 实际 / 模型
```

预算按“项目/集/镜”三级限制。超预算时它**说出来**，而不是默默失败。付费调用超时不能直接再发一次：先凭幂等键或供应商任务 ID 查状态；无法确认时标记 `unknown` 并保留预占，交给人工对账，防止一次超时变两次账单。

### Step 4 · VLM 质检（W5）— **K10**

图丢给视觉模型，**只输出 JSON**：

```json
{"broken_hands": false, "watermark": false, "composition_ok": true,
 "persona_consistency": 4, "confidence": 0.82,
 "reason": "发色与围裙一致，但眼神偏清醒"}
```

前 3 项是硬缺陷判定，第 4 项只用于排序“哪些最该人工复核”。VLM 是预筛，不是最终裁判；低置信度必须交给人。不合格项要携带结构化失败原因进入定向重做队列，**你确认新增费用后才重出**。默认一镜一个候选，禁止为了“看起来更稳”无差别生成多张。

### Step 5 · 归档打标（W5）

`outputs/ep03/shots/ep03_shot07_v2.png` —— 重命名 + 入库，之后能按集数/镜号/角色检索。

### Step 6 · 记忆与检索（W6，按证据）

最低交付是人设卡持久化：关掉程序再打开仍能按角色名取回约束。只有影子交付证明关键词/语义检索能减少 Top 3 耗时，才依次加 FTS5、sqlite-vec。

### Step 7 · 断点与 HITL（W7，按中断风险）

`拆镜 → 出图 → 质检 → 归档` 最低实现是线性断点；影子交付确实出现中断重跑时再升级显式状态机。三个节点必须停下来问你：

| 节点 | 问什么 |
|---|---|
| 批量出图前 | "本批预计费用为 {estimate}，项目/集/镜预算均满足，继续吗？" |
| 超预算或未知账单时 | "当前预算不足或上一任务账单未确认，请处理后再继续。" |
| 重做前 | "{count} 张建议定向重做，预计新增 {estimate}，继续吗？" |

### Step 8 · 可观测与可选 MCP（W8）

先把 trace / ledger / qc 生成经营报告。已有外部调用方时，再给一个稳定工具套 MCP 协议；Claude Code / Cursor 可直接调用，但不要求为首单盈利建设完整协议层。

### Step 9 · 交付报告（W9）

```
《雨夜便利店》EP3  交付报告
收入/目标报价     ¥____
人工工时           ____h → ____h
API + 直接成本     ¥____
首次可用率         ____%
平均每镜生成次数   ____
贡献毛利/有效时薪  ¥____ / ¥____h
```

> **报告不能砍**——它既是生产级证据，也是决定继续开发、调价或停止接单的经营仪表盘。

## 3 · 架构与数据流

### 3.1 一条数据流（10 周全部围绕它）

```
订单/自营选题 → 验收口径 + 手工基线 + 项目预算          → job 表/§8.2
 → 剧本(文本)
 → [M1 分镜]    分镜 JSON 列表        → shot 表
 → [M2 上下文]  约束包 + prompt 配方    → recipe 表（版本/参考素材/模型参数）
 → [M3 生图]    图片文件 + 三级预算台账 → asset / ledger 表
 → [M4 质检]    硬缺陷 + 连续性 + 置信度 → qc / rework_queue 表
 → [HITL]       人工终审与付费重做确认  → decision 表
 → [M5 记忆·条件]   可检索的历史素材     → persona / asset 表
 → [M6 状态机·条件] 流程可中断可恢复     → checkpoint 表
 → [M7 MCP·可选]    同一批工具对外暴露   （无新表）
 → [M8 验收]    质量/工时/单位经济报告  ← 来自 job + ledger + trace + qc
```

**每一跳都落一条 trace**（W1 就建好），业务指标必须能追溯到集数和镜号。后期所有报告都查记录生成，不手填“漂亮数字”。`job/recipe/decision` 可先用现有表字段或 JSON 快照表达，只有真实试单证明查询困难时才拆新表，避免 W1 过度建模。

### 3.2 装配顺序（P0 不许跳步，P1/P2 按证据启用）

```
① 公共基础  config/{settings,errors,logging_setup}.py
② LLM 出口  core/llm.py
③ 数据契约  schemas/*.py
④ 埋点      core/tracing.py          ← W1 就要有，补不出来
⑤ 交互外壳  shells/cli.py
⑥ 工具循环  agent/loop.py + tools/   ← W2 核心考试
⑦ 上下文裁剪 agent/context.py         ← W3
⑧ 成本治理  core/budget.py            ← W4
⑨ 感知      perception/qc.py          ← W5
⑩ 记忆检索  memory/                   ← W6，影子交付证明需要才加
⑪ 状态机    agent/graph.py            ← W7，中断问题成立才加
⑫ 协议层    mcp_server.py             ← W8，有外部调用方才加
```

①→⑤ 是 W1，⑥ W2，⑦ W3，⑧ W4，⑨ W5，构成可收费 P0。⑩–⑫ 只能在不破坏前序依赖的前提下按证据选择；“没做不需要的模块”不算跳步。

### 3.3 模块总表

| 模块 | 一句话职责 | 存哪 | 知识点 | 哪周 |
|---|---|---|---|---|
| `shells/cli.py` | 你打字的地方 | — | K0 | W1 |
| `core/llm.py` | 所有模型调用的**唯一出口** | — | K1 | W1 |
| `core/tracing.py` | 每次调用记账 | `trace` | K9 | W1 |
| `agent/loop.py` | 手写 ReAct 循环（心脏） | — | **K2** | W2 |
| `agent/context.py` | 按镜号裁剪上下文 | — | K3 | W3 |
| `agent/graph.py` | 按中断风险选择显式状态机或线性断点 | `checkpoint` | K8 | W7 条件 |
| `tools/storyboard.py` | 剧本 → 分镜 | `shot` | K1 K2 | W2 |
| `tools/prompt_factory.py` | 拼生图 prompt | — | K3 | W3 |
| `tools/image_gen.py` | 调生图 API | `outputs/` | — | W4 |
| `core/budget.py` | 预算闸门 | `ledger` | K6 | W4 |
| `perception/qc.py` | 看图挑毛病 | `qc` | K10 | W5 |
| `tools/archive.py` | 重命名 + 打标 + 入库 | `asset` | K5 | W5 |

### 3.4 三条记住就不会迷路的规则

1. **所有模型调用只走 `core/llm.py` 一个出口** —— 超时、重试、降级、记 trace 都在那，别到处写。
2. **工具是独立的纯函数** —— 不依赖 agent，所以能同时给你自己的 loop 和 MCP 用。
3. **数据全在 SQLite 一张库里** —— 台账、trace、质检、人工决策和配方版本都能按订单/集/镜串起来，所有报告才有数可依。
4. **模型只提建议，人负责商业承诺** —— 报价、最终交付、超预算、付费重做和合规发布必须由人确认。

## 4 · 十周里程碑

> 节奏纪律：分支 → 实现 → `ruff + pytest` → 写日志 → 合 main → 打 tag → **当天录 1 分钟演示**。

## 5 · 防烂尾机制（本文件最重要的部分）

### 5.1 八条铁律

| # | 铁律 | 具体做法 |
|---|---|---|
| 1 | **演示即验收** | 没有 1 分钟演示 = 里程碑未完成。演示当天录，不攒、不补拍。 |
| 2 | **一次只开一个开发任务** | WIP 上限 = 1；当前文件/验收没完成，不开下一个功能分支。 |
| 3 | **MVP / 增强分档** | 时间不够只交 MVP；增强档不做不扣分，不能反向阻塞 MVP。 |
| 4 | **止损线硬执行** | 任一卡点超过上表时限，立即走降级方案，不用“再研究一天”拖延。 |
| 5 | **先跑通再优化** | 任何模块先用假数据/小样本走通，再换真实付费 API；禁止边写边重构。 |
| 6 | **真实数据决定下一周** | W5 后每个 P1 功能必须引用 §8.2 的痛点记录；不能减少 Top 3 成本/工时/质量问题就不做。 |
| 7 | **可停止也是成功** | 若两次小样都无法改善三项核心指标中的两项，冻结开发，保留已能用的工具并转向调价、换品类或停止该服务。 |
| 8 | **掌握即验收** | 每个核心功能必须能闭卷解释、独立写核心流程、测成功/失败、定位故障并完成一次小需求变更；只会运行不算完成。 |

**为什么这么设计**：新手烂尾的头号原因不是技术难，是**在前置依赖上耗光预算**（底座、环境、全家桶教程）。所以本计划把风险最高的东西全部后置，把"能最快看到成果"的东西前置。

### 5.2 每周继续 / 降级 / 停止决策门

1. **继续**：有可演示物，且本周指标或能力对 P0 闭环有直接贡献；只开下一项 MVP。
2. **降级**：超过止损线、连续 2 次返工仍不稳定，或预计剩余工作 > 本周可用时间；立即砍增强，把任务缩到 5 小时内。
3. **跳过**：P1/P2 没有 §8.2 的真实证据；记录“不做的理由”，不留半成品分支。
4. **冻结项目**：连续两周无可演示物，或两次小样的质量/工时/单可用镜头成本均未改善；不再添加功能，先做经营复盘。

冻结不是失败，而是用有限时间避免沉没成本。恢复开发必须带来一条新的真实订单证据或明确的技术解法。

### 5.3 周日自检（15 分钟，写在 §10）

1. **这周有没有产生一个能演示的东西？**（有 / 没有）
2. **它让质量、工时、成本中的哪项变好？证据在哪？**
3. **卡在哪一步，卡了多久？是否已触发止损？**
4. **下周唯一的 MVP 是什么？**（必须一句话说清，且 WIP=1）
5. **本周哪个核心逻辑能闭卷讲清并独立改动？证据是什么？**

### 5.4 砍功能时先保护赚钱闭环

| 如果砍掉 | 允许的最低替代 | 不能牺牲的东西 |
|---|---|---|
| MCP（W8） | CLI/函数调用演示 | 不影响生产闭环，优先砍 |
| 状态机（W7） | 线性步骤 + 断点记录 | 不能让中断后整单重做 |
| 向量检索（W6） | 人设卡主键查询或 FTS5 | 能找回当前订单的角色/场景约束 |
| VLM 主观打分（W5） | 2 个稳定硬缺陷判定 + 人工终审 | 失败原因、人工决定和返工次数必须留痕 |
| VTuber 外壳（W10） | CLI | 全部商业指标不受影响，直接砍 |
| 真实订单 | 10 镜自营样片 + 目标报价敏感性分析 | 不得把目标报价写成收入或声称已盈利 |

### 5.5 Tag 规则

- 里程碑完成 → 合 `main` → 打 tag（v0.1.0 起）→ tag message 附演示文件名。
- 跳过的里程碑不打 tag，在 §10 记录"跳过原因 + 预计补做时间"。
- 禁止对 `main` 使用 `--force`；提交信息走 Conventional Commits（见 `01` §7）。

## 6 · 怎么保证它能进入真实生产

> 生产级不是模块多，而是能在质量、成本、交付和追责上给出证据。

### 6.1 七条分界线

| # | Demo 长这样 | 生产级长这样 | 本项目靠什么达标 |
|---|---|---|---|
| 1 | 输入是玩具数据 | **真实业务数据闭环** | W6 影子交付，W9 真做 1 集 + §8.2 |
| 2 | "感觉更快了" | **数字可量化** | ledger + trace 查表出报告，不是拍脑袋 |
| 3 | 改 prompt 靠感觉 | **有评测集，改必回归** | `evals/` 三个 jsonl + `run_eval.py` |
| 4 | 付费超时就盲目重试 | **幂等提交、查询状态、未知账单对账** | reserve / job_id / settle / unknown 状态 |
| 5 | 跑到一半重来 | **可中断可恢复** | `agent/graph.py` + checkpoint 表 |
| 6 | VLM 说好就直接交付 | **模型预筛 + 人工终审** | 置信度、人工决定、返工原因全部留痕 |
| 7 | 只算 API 账单 | **算贡献毛利和有效时薪** | §8.2 + ledger + trace 联合报告 |

### 6.2 生产级证据清单（哪周产出什么证据）

| 周 | 证据物 | 存在哪 |

### 7.3 叙事分层（二次元人设是双刃剑）

- **风险**：面试官可能读成"二次元玩具项目"，而不是背后那套工程。
- **做法**：仓库和文档一律用专业工程语言；人设只作为"交互层设计"一章，讲清产品理由（高频长时间使用时降低认知负荷）。
- **面试顺序**：**先讲工程（工具调用 / 预算 / 评测），最后 30 秒放人设演示当记忆点**。

### 7.4 真正能积累的商业资产

| 资产 | 为什么模型厂商难替代 | 怎么积累 |
|---|---|---|
| 角色/服装/场景约束包 | 来自具体 IP 与客户验收，不是通用 prompt | 每单版本化，记录哪些约束被人工接受 |
| 失败样本与返工原因 | 公开模型不知道你的客户为何拒片 | 保存失败类型、人工决定和重做结果 |
| 单位经济数据 | 不同题材、画风、镜头复杂度成本差异很大 | §8.2 按同一口径连续记录 |
| 交付 SOP | 把“什么时候必须由人决定”变成可复制流程 | HITL 节点、验收清单、预算策略 |
| 复购关系 | 稳定收入来自重复交付，不来自一次爆款 | 从小样→标准单→多集包逐级验证 |

Agent 的代码可以被模仿，**带结果标签的数据和经客户验证的流程**才是长期壁垒。

## 8 · 兼职线（真实需求来源）

### 8.1 定位与红线

- **先服务、后产品**：v1 是自己的生产操作系统，不做 SaaS、不承诺流量、不预测爆款。先靠承制/协作服务获得现金流和数据。
- **先卖窄结果**：优先提供“分镜 + 角色/场景约束包 + 可用静帧 + 质检/成本报告”；是否承接剪辑、配音、发布必须另行报价，不默认包含。
- **价格不抄行情**：报价由交付范围、预计人工、API 上限、风险缓冲和目标有效时薪反推。网上无法核验的“均价/爆款率”不进入决策。
- **合规是交付项**：确认剧本/IP/参考图使用权；保留客户确认；公开发布前核对备案、AI 生成标识及平台规则。Agent 只提醒和留痕，不代替法律判断。

### 8.3 单位经济公式与继续开发门

```text
直接成本 = API + 外包 + 素材授权 + 退款/补偿 + 其他随单发生费用
贡献毛利 = 实收收入 - 直接成本
有效时薪 = 贡献毛利 / 本人实际投入小时
单可用镜头成本 =（生成 + 质检 API 成本）/ 人工最终通过镜头数
首次可用率 = 首次生成即被人工通过的镜头数 / 首次生成镜头数
```

- 自营样片没有真实收入，只能用多个目标报价做敏感性分析，不能宣称盈利。
- W6 继续开发门：相对 `BASE-01`，首次可用率、总工时、单可用镜头成本至少两项改善，且人工接受率不下降。
- W9 商业通过门：真实单贡献毛利为正；有效时薪达到本人预先填写的目标；返工未突破合同范围。未通过时先调价/缩范围/换品类，不通过堆功能掩盖。
- “稳定赚钱”要用连续 3 个同口径订单的中位数判断；单个成功案例只能证明可行，不能证明稳定。

### 8.4 前景判断（截至 2026-09，只保留可核验事实）

- **机会存在**：快手 2025 年全年业绩公告明确提到漫剧高速发展、平台推出扶持计划和 AI 漫剧智能体，说明平台和供给侧都在投入。
- **竞争会更激烈**：平台自己也在提供 AI 生产能力；“会调用模型”很快商品化，真正可守住的是角色/场景资产、失败样本、成本数据、交付 SOP 和客户关系。
- **合规门槛上升**：2026-09-01 起施行的《微短剧发展管理办法》要求 AI 生成/制作的微短剧按规定在每集明显位置添加提示标识，并强调备案、审核、知识产权和数据安全。
- **因此本项目的正确位置**：不做通用“一键漫剧神器”，做可审计的生产控制层；上游模型随时可换，下游交付证据和经营数据留在自己手里。
