## 0 · 三句话定位

1. **做什么**：给 AI 漫剧（动态漫画）做「副导演 Agent」——输入剧本，输出分镜表、生图 prompt、成图质检与成本台账，把单集制作工时压下来。
2. **为什么值钱**：不是聊天机器人 demo，是**有预算闸门、有评测集、有成本台账、能中断恢复、能对外集成**的一整套工程；并且要拿去真实接单验证。
3. **怎么算成**：W9 拿出一集真实成片 + 工时/成本对比数字；W10 有一份能讲 3 分钟的 README。**没有数字的"做完了"不算完。**

## 1 · 产品定位与范围

### 1.1 要解决什么

AI 漫剧代工的真实痛点是**重复劳动多、人物一致性难保持、成本失控**：一集 20 镜，每镜都要手写 prompt、检查崩手崩脸、记账。人工做一集 6 小时，其中 4 小时是机械劳动。

### 1.2 P0 功能（必须做，缺一不可）

| # | 功能 | 一句话 | 哪周 |
|---|---|---|---|
| 1 | 分镜生成 | 剧本 → 结构化分镜 JSON（20 镜） | W2 |
| 2 | 上下文工程 | 按镜号裁剪上下文，只喂当前镜相关角色卡 | W3 |
| 3 | 生图编排 + 预算治理 | reserve → 调用 → settle，超限明确拒绝并记账 | W4 |
| 4 | VLM 质检 | 自动挑废片（崩手/水印/构图/一致性） | W5 |
| 5 | 记忆与检索 | 重启后还记得人设卡，能按镜号搜素材 | W6 |
| 6 | 状态机 + HITL | 流程可中断可恢复，关键节点问人 | W7 |
| 7 | MCP + 可观测 | 工具对外暴露；trace 落库生成报告 | W8 |
| 8 | 真实验收 | 用 Agent 完整交付 1 集，出对比报告 | W9 |

### 1.3 明确不做（红线，写了就删）

| 不做 | 原因 |
|---|---|
| 模型微调（LoRA / SFT / DPO / RLHF） | 那是另一个岗位，JD 里和 Agent 应用开发分开招 |
| **引入 Agent 框架作为运行时依赖**（LangChain / AutoGen / CrewAI） | 手写内核是差异化；但**允许手写状态机并做概念对标**（见 §7.1） |
| 向量数据库集群（Milvus / Qdrant） | 单机单用户，sqlite-vec 足够 |
| ComfyUI 本地部署 | ≥8G 显存，除非云 API 挂了 |
| 多 Agent 编排 | 单 Agent + 工具已够，编排是范围陷阱 |
| 底座 Open-LLM-VTuber 作前置依赖 | v2.0 全量重写中，降级为 W10 可选外壳 |

### 1.4 成功标准（W10 自测）

- [ ] 用 Agent 完整交付 **1 集**真实成片（接单或自做均可）
- [ ] 工时对比有数字：手工基线 __h → Agent __h（目标 -30% 以上）
- [ ] 成本台账误差 ≤5%，且发生过至少一次真实超限拒绝
- [ ] 3 个评测集齐全（分镜 / 一致性 / 质检），改 prompt 必回归
- [ ] 至少 1 个工具被外部 MCP 客户端成功调用
- [ ] README 里能讲清架构，且这 6 条都能演示

## 2 · 系统全景（先读这个，再看周计划）

**场景**：接了一单，剧本《雨夜便利店》第 3 集，800 字，要出 20 镜静帧。

### Step 0 · 建项目与角色卡（W3）

录入 2 张角色卡，存 SQLite `persona` 表：

```
小雨：17岁便利店店员，黑色齐耳短发，红色围裙，圆脸，眼神困倦
老陈：50岁常客，灰色夹克，秃顶，戴老花镜
```

**为什么先有它**：后面每一镜的生图 prompt 都从这里取特征词——这是"人物一致性"的根。

### Step 1 · 分镜生成（W2）— **K2 Function Calling 完整链路**

```
你的话 + 工具说明书 → LLM
LLM 决定："我要调 generate_storyboard，参数是这段剧本"
你的代码解析 JSON → 执行函数 → 结果回喂 LLM
LLM 用人话回你："拆好了，20 镜，预计 3 分 20 秒"
```

```json
{"shot_no": 7, "desc": "小雨在货架前整理泡面，抬头看向门口",
 "dialogue": "欢迎光临……咦？", "camera": "中景，固定机位，轻微推近",
 "duration_s": 8, "characters": ["小雨"]}
```

### Step 2 · 上下文裁剪 + 拼 prompt（W3）— **K3 Context Engineering**

笨办法是把 20 镜 + 全部角色卡一股脑塞进去（贵且角色特征互相污染）。正确做法：生成第 7 镜时**只喂**①第 7 镜描述 ②小雨的卡（老陈不进窗口）③前 2 镜画面。

```
裁剪前 3200 token → 裁剪后 640 token（省 80%）
1girl, black bob hair, red apron, round face, sleepy eyes,
convenience store shelf, arranging instant noodles, …
```

> **简历上"上下文工程"那条是这么来的**：不是写更好的提示词，是**决定什么不该进窗口**。

### Step 3 · 出图 + 扣钱（W4）— **K6 成本治理**

```
reserve(预估 ¥0.15) → 调用生图 API（超时 60s，失败退避重试 2 次）→ settle(实际)
台账写一行：时间 / 集数 / 镜号 / 预估 / 实际 / 模型
```

超预算时它**说出来**，而不是默默失败：
> "今天额度只剩 ¥0.8 了，这镜要 ¥0.15，出完就没了。要出吗？"

### Step 4 · VLM 质检（W5）— **K10**

图丢给视觉模型，**只输出 JSON**：

```json
{"broken_hands": false, "watermark": false, "composition_ok": true,
 "persona_consistency": 4, "reason": "发色与围裙一致，但眼神偏清醒"}
```

前 3 项二元判定（稳定可验收），第 4 项 5 分制打分（排序"哪些最该重做"）。不合格进重做队列，**你确认后才重出**。

### Step 5 · 归档打标（W5）

`outputs/ep03/shots/ep03_shot07_v2.png` —— 重命名 + 入库，之后能按集数/镜号/角色检索。

### Step 6 · 记忆与检索（W6）

问"上一集小雨穿的什么？"→ 混合检索（FTS5 + sqlite-vec）→ 答"红色围裙 + 白色内搭，与本集一致"。**关掉程序再打开它还记得**。

### Step 7 · 状态机（W7）

`拆镜 → 出图 → 质检 → 归档` 每步存断点，重启从断点继续。三个节点必须停下来问你：

| 节点 | 问什么 |
|---|---|
| 批量出图前 | "20 镜预计 ¥3.0，今天额度 ¥5，出吗？" |
| 超预算时 | "只剩 ¥0.8 了，还出吗？" |
| 重做前 | "3 张建议重做，要多花 ¥0.45，重做吗？" |

### Step 8 · MCP（W8）

W1–W7 写的 6 个工具**不用重写**，套一层 MCP 协议，Claude Code / Cursor 里直接说"把 ep03 分镜导出成 Markdown"就能调。

### Step 9 · 交付报告（W9）

```
《雨夜便利店》EP3  交付报告
工时       6.2h  →  3.8h   (-39%)
生图成本          ¥12.30
废片率            18%
质检通过率        82%
```

> **这是唯一一条别砍的**——它是"生产级"背书的唯一来源。

## 3 · 架构与数据流

### 3.1 一条数据流（10 周全部围绕它）

```
剧本(文本)
 → [M1 分镜]    分镜 JSON 列表        → shot 表
 → [M2 上下文]  按镜号裁剪 → prompt     （不入库，每次现算）
 → [M3 生图]    图片文件 + 台账        → asset / ledger 表
 → [M4 质检]    质检 JSON              → qc 表
 → [M5 记忆]    可检索的历史素材        → persona / asset 表
 → [M6 状态机]  流程可中断可恢复        → checkpoint 表
 → [M7 MCP]     同一批工具对外暴露      （无新表）
 → [M8 验收]    工时/成本对比报告       ← 来自 ledger + trace
```

**每一跳都落一条 trace**（W1 就建好）——后期所有报告都是查表生成的，不是各写各的。**这是全项目最容易烂尾的隐性依赖。**

### 3.2 装配顺序（不许跳步）

```
① 公共基础  config/{settings,errors,logging_setup}.py
② LLM 出口  core/llm.py
③ 数据契约  schemas/*.py
④ 埋点      core/tracing.py          ← W1 就要有，补不出来
⑤ 交互外壳  shells/cli.py
⑥ 工具循环  agent/loop.py + tools/   ← W2 核心考试
⑦ 上下文裁剪 agent/context.py         ← W3
⑧ 成本治理  core/budget.py            ← W4
⑨ 感知      perception/qc.py          ← W5
⑩ 记忆检索  memory/                   ← W6
⑪ 状态机    agent/graph.py            ← W7
⑫ 协议层    mcp_server.py             ← W8
```

①→⑤ 是 W1，⑥ W2，⑦ W3，⑧ W4，⑨ W5，⑩ W6，⑪ W7，⑫ W8。

### 3.3 模块总表

| 模块 | 一句话职责 | 存哪 | 知识点 | 哪周 |
|---|---|---|---|---|
| `shells/cli.py` | 你打字的地方 | — | K0 | W1 |
| `core/llm.py` | 所有模型调用的**唯一出口** | — | K1 | W1 |
| `core/tracing.py` | 每次调用记账 | `trace` | K9 | W1 |
| `agent/loop.py` | 手写 ReAct 循环（心脏） | — | **K2** | W2 |
| `agent/context.py` | 按镜号裁剪上下文 | — | K3 | W3 |
| `agent/graph.py` | 显式状态机 + checkpoint | `checkpoint` | K8 | W7 |
| `tools/storyboard.py` | 剧本 → 分镜 | `shot` | K1 K2 | W2 |
| `tools/prompt_factory.py` | 拼生图 prompt | — | K3 | W3 |
| `tools/image_gen.py` | 调生图 API | `outputs/` | — | W4 |
| `core/budget.py` | 预算闸门 | `ledger` | K6 | W4 |
| `perception/qc.py` | 看图挑毛病 | `qc` | K10 | W5 |
| `tools/archive.py` | 重命名 + 打标 + 入库 | `asset` | K5 | W5 |
| `memory/` | 人设卡库 + 素材检索 | `persona`/`asset` | K5 | W6 |
| `mcp_server.py` | 把工具暴露给外部 | — | K7 | W8 |
| `scripts/run_eval.py` | 跑评测集出报告 | `docs/evals/` | K4 | W2 起 |

### 3.4 三条记住就不会迷路的规则

1. **所有模型调用只走 `core/llm.py` 一个出口** —— 超时、重试、降级、记 trace 都在那，别到处写。
2. **工具是独立的纯函数** —— 不依赖 agent，所以能同时给你自己的 loop 和 MCP 用。
3. **数据全在 SQLite 一张库里** —— 台账、trace、质检、记忆都从这出，所有报告才有数可依。

## 5 · 防烂尾机制（本文件最重要的部分）

### 5.1 五条铁律

| # | 铁律 | 具体做法 |
|---|---|---|
| 1 | **演示即验收** | 没有 1 分钟演示 = 里程碑未完成。演示**当天录**，不攒、不补拍。 |
| 2 | **MVP / 增强分档** | 时间不够只交 MVP，里程碑照样算过。增强档不做不扣分。 |
| 3 | **止损线硬执行** | 任一卡点超过上表时限，立即停手走降级方案，不许硬扛。 |
| 4 | **周日 15 分钟自检** | 每周日回答三个问题（§5.3），连续两周无产出 → 强制砍增强 + 缩减范围。 |
| 5 | **先跑通再优化** | 任何模块先用最笨的方式跑通一次，再谈优化。禁止"边写边重构"。 |

**为什么这么设计**：新手烂尾的头号原因不是技术难，是**在前置依赖上耗光预算**（底座、环境、全家桶教程）。所以本计划把风险最高的东西全部后置，把"能最快看到成果"的东西前置。

### 5.2 连续两周无产出的强制动作

1. 砍掉当前里程碑的所有增强档；
2. 把剩余范围砍到能在 5 小时内完成；
3. 还是做不完 → **跳过该里程碑，直接进下一个**（在 §10 记录表写明跳过原因 + 预计补做时间）。

### 5.3 周日自检（15 分钟，写在 §10）

1. **这周有没有产生一个能演示的东西？**（有 / 没有）
2. **卡在哪一步，卡了多久？**（超过止损线了吗）
3. **下周的 MVP 是什么？**（必须一句话能说清）

### 5.4 砍功能时的竞争力保护清单

砍东西不可避免，但**每砍一样，必须用别的方式补回关键词**：

| 如果砍掉 | 会损失 | 必须补上 |
|---|---|---|
| MCP（W8） | JD 高频词 | README 写清"工具层按 MCP 协议设计，可一键封装" |
| 状态机（W7） | LangGraph 关键词 | 至少保留 `docs/langgraph-mapping.md` 概念映射文档 |
| 向量检索（W6） | RAG 关键词 | 保留 FTS5 **+ 写清"何时不需要向量"的判断依据**（这比硬上向量更显功力） |
| VLM 打分（W5） | 多模态关键词 | 保留 2 个二元判定，够证明能力 |
| VTuber 外壳（W10） | 人设交互亮点 | 用 CLI + 人设卡文案演示，影响很小 |
| **真实接单（W9）** | **生产级背书（损失最大）** | **这条别砍**，至少自做 1 集并填工时成本表 |

### 5.5 Tag 规则

- 里程碑完成 → 合 `main` → 打 tag（v0.1.0 起）→ tag message 附演示文件名。
- 跳过的里程碑不打 tag，在 §10 记录"跳过原因 + 预计补做时间"。
- 禁止对 `main` 使用 `--force`；提交信息走 Conventional Commits（见 `01` §7）。

## 6 · 怎么保证它不是 Demo（生产级判定标准）

> 面试官一眼能看出 demo 和生产级的区别。**这一节是本项目最该反复读的部分。**

### 6.1 七条分界线

| # | Demo 长这样 | 生产级长这样 | 本项目靠什么达标 |
|---|---|---|---|
| 1 | 输入是玩具数据 | **真实业务数据闭环** | W9 真做 1 集（接单或自做）+ 工时成本表 |
| 2 | "感觉更快了" | **数字可量化** | ledger + trace 查表出报告，不是拍脑袋 |

### 8.1 定位与红线
