### 1.1 `config/errors.py` 异常树（步骤 3）

**知识 3 分钟**

为什么要有异常树？因为不同错误的**处理方式不同**：

- `BudgetError` 必须**告诉用户**（不默默失败，这是 K6 考点）
- `SchemaError` 必须**带原始返回**（否则线上无法排查）
- `LLMError` 可以**重试**  
  如果全用 `raise Exception("xxx")`，调用方没法区分，只能一把兜住——那就失去了精细处理的能力。

**契约**

```python
class KantokuError(Exception):
    def __init__(self, message: str, *, detail: str | None = None) -> None: ...

class ConfigError(KantokuError): ...    # 配置缺失/密钥未设
class LLMError(KantokuError): ...       # 调用失败（可重试）
class SchemaError(KantokuError): ...    # 解析失败（必须带原始返回）
class BudgetError(KantokuError): ...    # 超预算（必须明确拒绝）
```

#### 跟着逐行写（知识点在用到的那一行才讲，不提前堆概念）

> **用法**：新建/清空 `src/kantoku/errors.py`，从「第 1 行」开始往下写。  
> 每行分三块：**【写】** 这一行写什么 ／ **【讲】** 为什么需要它 ／ **【验】** 怎么确认没写错。

**第 0 步 · 先想清楚要防什么错**（写之前 30 秒）

| 你项目里会遇到的失败      | 想要的处理方式           | 所以叫           |
| --------------- | ----------------- | ------------- |
| 密钥没配 / yaml 字段缺 | 立刻停，告诉用户去配        | `ConfigError` |
| 调模型超时、被限流       | 等一下重试             | `LLMError`    |
| 模型返回的 JSON 不合格式 | 打印原始返回，人工排查       | `SchemaError` |
| 今天的钱花超了         | **必须告诉用户**，不许偷偷跳过 | `BudgetError` |

> 这四件事处理方式完全不同 → 所以要有四个不同的异常。  
> 它们又都是"本项目的错误" → 所以共同继承一个 `KantokuError`。

**第 2–4 行**

**第 7 行 · 这一行语法最多，拆开讲**

- 【写】
  ```python
      def __init__(self, message: str, *, detail: str | None = None) -> None:
  ```

- 【讲】四个新东西，逐个说：
  1. `def __init__` —— 创建对象时**自动执行**的函数。你写 `KantokuError("超时")` 时它就被调用
  2. `self` —— 代表"这个对象本身"，`self.xxx = ...` 就是把数据存到对象上，后面能用 `e.xxx` 取出来
  3. `*` —— 它后面的参数**必须写名字**传：  
     `KantokuError("a", detail="b")` ✅ ／ `KantokuError("a", "b")` ❌
  4. `str | None` —— 类型注解，表示"字符串或者 None 都行"；`= None` 是默认值，所以可以不传
- 【验】`uv run python -c "from kantoku.errors import KantokuError; KantokuError('a', 'b')"`  
  → 应该**报错**（positional argument），报错说明 `*` 生效了。

---

**第 8 行 · 一个"大家都这么说但其实说错了"的点**

- 【写】`        super().__init__(message)`
- 【讲】`super()` = 父类。这行是"把 message 交给父类 Exception 保管"。  
  **诚实的实测结论**（Python 3.13 验证）：现代 Python 里 `BaseException.__new__`  
  已经把构造参数存进 `e.args` 了，所以**在简单单继承下，不写这行 `str(e)` 也不会空**。  
  （网上广为流传的"不写 super 就变空"是过时说法。）  
  那为什么还要写？三个实在理由：
  1. **明确**：读代码的人一眼看出"这条消息是异常的主消息"
  2. **安全**：将来加多重继承、或改动 `__init__` 签名时不会踩协同初始化的坑
  3. **一致**：`e.args` 与 `e.message` 永远同步（有些库用 `args` 重建异常对象）
- 【验】`uv run python -c "from kantoku.errors import KantokuError; e=KantokuError('a'); print(e.args, e.message)"`  
  → 输出 `('a',) a`

> **为什么不是 `super().__init__(detail)`？**  
> 实测：`Exception("超时", "重试2次")` 的 `str()` 会变成 `('超时', '重试2次')`——  
> **元组形式，很难看**。父类只认"一条主消息"，`detail` 是我们自己扩展的字段，  
> 所以自己存 `self.detail`、自己在 `__str__` 里拼，显示完全可控。

---

**第 9–10 行**

- 【写】
  ```python
          self.message = message
          self.detail = detail
  ```
- 【讲】把两个参数**存到对象上**。后面 `core/tracing.py` 要读 `e.message` 和 `e.detail` 写进数据库。
- 【验】`uv run python -c "from kantoku.errors import KantokuError; e=KantokuError('x', detail='y'); print(e.message, e.detail)"`  
  → 输出 `x y`

**第 11–14 行 · 控制报错长什么样**

- 【写】
  ```python
      def __str__(self) -> str:
          if self.detail:
              return f"{self.message}｜{self.detail}"
          return self.message
  ```
- 【讲】`__str__` 在 `print(e)` / `str(e)` / 异常自动打印时被调用。  
  这里做两件事：有 `detail` 就拼在后面（中间竖线分隔），没有就只返回 `message`。
- 【验】


  ```powershell
  uv run python -c "from kantoku.errors import KantokuError; print(str(KantokuError('解析失败'))); print(str(KantokuError('解析失败', detail='raw={bad}')))"
  ```
  → 第一行 `解析失败`，第二行 `解析失败｜raw={bad}`。**第一行如果输出空 → 第 8 行漏了 `super()`**

---

**第 15 行起 · 四个子类**

- 【写】（每个之间空两行）
  ```python
  class ConfigError(KantokuError):
      """配置文件缺失、字段不合法，或环境变量（密钥）未设置。"""


  class LLMError(KantokuError):
      """LLM 调用失败：超时、重试耗尽、返回结构不符合预期。"""


  class SchemaError(KantokuError):
      """结构化输出解析失败。必须携带原始返回，否则线上无法排查。"""


  class BudgetError(KantokuError):
      """超出预算红线。调用方必须明确告知用户，禁止默默跳过。"""
  ```
- 【讲】这就是**异常树的价值**：
  ```python
  except KantokuError:   # 一把兜住全部四种
  except LLMError:       # 只接 LLM 的 → 可以重试
  ```
  之所以能这样，是因为 `isinstance(LLMError("x"), KantokuError)` 是 `True`（子类属于父类）。
- 【验】
  ```powershell
  uv run python -c "from kantoku.errors import *; print([isinstance(c('t'), KantokuError) for c in (ConfigError, LLMError, SchemaError, BudgetError)])"
  ```
  → `[True, True, True, True]`

### 1.2 `config/settings.py` 配置入口（步骤 3）

#### 第 0 步 · 先想清楚要管哪些东西（写之前 1 分钟）

#### 第 1–7 行 · 导入

- 【写】
  ```python
  from __future__ import annotations

  import os
  from functools import lru_cache
  from pathlib import Path

  import yaml
  from pydantic import BaseModel
  from pydantic_settings import BaseSettings, SettingsConfigDict

  from kantoku.config.errors import ConfigError
  ```
- 【讲】逐个说：
  - `os` —— 读环境变量（`os.environ.get(...)`）
  - `Path` —— 处理文件路径，比字符串拼接安全（Windows 反斜杠的坑它帮你避）

  - `BaseModel`（pydantic）—— 定义数据结构的类，自带**类型校验**
  - `BaseSettings`（pydantic-settings）—— 支持从环境变量读的 BaseModel

    注意是**点开头**的相对路径：`from .` 表示"当前包内"，`from ..` 表示"上一级包"。
    这就是 `docs/11 §2` 装配顺序里"配置与异常排第一"的原因：settings 依赖 errors

#### 然后 · 总入口 Settings

- 【写】
  ```python
  class Settings(BaseSettings):
      """配置总入口。yaml 提供结构，环境变量提供密钥。"""

      model_config = SettingsConfigDict(env_prefix="KANTOKU_", extra="ignore")

      app: AppSettings = AppSettings()
      llm: LlmSettings = LlmSettings()
      budget: BudgetSettings = BudgetSettings()
      storage: StorageSettings = StorageSettings()
      vtuber: VtuberSettings = VtuberSettings()
  ```
- 【讲】
  - `env_prefix="KANTOKU_"` —— 允许用 `KANTOKU_XXX` 这类环境变量覆盖
  - `extra="ignore"` —— yaml 里多写了字段也不报错（容错）
  - 每个字段给默认值 → `Settings()` 永远能创建，不会因缺配置而 import 崩溃

#### 然后 · `_require_env()`：密钥缺失就明确报错

- 【写】
  ```python
  def _require_env(name: str) -> str:
      value = os.environ.get(name)
      if not value:
          raise ConfigError(
              f"环境变量 {name} 未设置",
              detail="请在项目根目录的 .env 里配置，或先执行："
              f'$env:{name}="你的密钥"（PowerShell）',
          )
      return value
  ```
- 【讲】**这里用上了上一节的 `ConfigError` 和它的 `detail` 参数**。
  为什么不用 `raise Exception`？因为调用方能 `except ConfigError` 精确捕获，
  给用户一句"去配 .env"的友好提示，而不是一堆看不懂的 traceback。
- 【验】
  ```powershell
  uv run python -c "from kantoku.config import _require_env; _require_env('NOT_EXIST_KEY')"
  ```
  → 应该看到 `环境变量 NOT_EXIST_KEY 未设置｜请在项目根目录的 .env 里配置...`

---

#### 然后 · `_read_yaml()`：读文件 + 兜底

- 【写】
  ```python
  def _read_yaml() -> dict:
      path = CONFIG_PATH if CONFIG_PATH.exists() else EXAMPLE_PATH
      if not path.exists():
          raise ConfigError("找不到配置文件", detail=f"期望路径：{CONFIG_PATH}")
      with path.open(encoding="utf-8") as f:
          return yaml.safe_load(f) or {}
  ```
- 【讲】两个细节：
  - **兜底**：没有 `settings.yaml`（还没复制）就退回 example → 别人 clone 你的仓库也能跑
  - `encoding="utf-8"` → yaml 里有中文注释，不加会乱码/报错
- 【验】`uv run python -c "from kantoku.config import _read_yaml; print(list(_read_yaml().keys()))"`
  → `['app', 'llm', 'budget', 'storage', 'vtuber']`

#### 最后 · `get_settings()` + 缓存

- 【写】
  ```python
  @lru_cache(maxsize=1)
  def get_settings() -> Settings:
      raw = _read_yaml()
      return Settings(
          app=AppSettings(**raw.get("app", {})),
          llm=LlmSettings(**raw.get("llm", {})),
          budget=BudgetSettings(**raw.get("budget", {})),
          storage=StorageSettings(**raw.get("storage", {})),
          vtuber=VtuberSettings(**raw.get("vtuber", {})),
      )
  ```
- 【讲】
  - `**raw.get("llm", {})` —— 把字典拆成关键字参数（就是 K1 视频里那个 `**`）
  - `@lru_cache(maxsize=1)` —— 第一次调用读盘，之后直接返回缓存的同一份。
    **副作用**：改了 yaml 要重启进程才生效（知道就行，别到时候以为改了没反应）
- 【验】
  ```powershell
  uv run python -c "from kantoku.config import get_settings; s=get_settings(); print(s.llm.model_chat, '|', s.llm.model_vision, '|', s.budget.image_daily_cny)"
  ```

### 1.3 `config/logging_setup.py` 日志（步骤 3）

#### 第 0 步 · 先想清楚为什么要有两个出口

| 出口 | 给谁看 | 级别 | 特点 |
|---|---|---|---|
| **控制台** | 正在操作的你 | INFO 以上 | 带颜色、简洁，一眼看懂 |
| **文件** | 出事之后排查的你 | DEBUG 全量 | 滚动切分、保留 7 天 |

**为什么不能只留一个**：只留控制台 → 关掉终端就没了；只留文件 → 平时看不到进度。
这叫**双通道**，是所有生产级项目的基本配置。

---

#### 第 1–4 行 · 导入

- 【写】
  ```python
  from __future__ import annotations

  import sys
  from pathlib import Path

  from loguru import logger
  ```
- 【讲】三个导入各自干嘛：
  - `sys` —— 拿 `sys.stderr`（控制台输出目标）
  - `Path` —— 拼日志目录路径
  - `logger`（loguru）—— 和标准库 `logging` 最大的区别：**它是现成的全局对象**，
    不需要 `logging.getLogger(__name__)` 那套，import 就能用
- 【验】无

---

#### 第 6–8 行 · 定义目录与函数签名

- 【写】
  ```python
  LOG_DIR = Path("data") / "logs"


  def setup_logging(level: str = "INFO") -> None:
  ```
- 【讲】为什么用 `Path("data") / "logs"` 而不是字符串 `"data/logs"`？
  Path 会自动处理 Windows 的反斜杠，跨平台不会错。
- 【验】无

---

#### 函数体第 1 行 · 清掉默认输出 ⚠️ 最容易忘

- 【写】（缩进 4 空格）
  ```python
      logger.remove()
  ```
- 【讲】loguru **默认自带一个输出到 stderr 的 sink**（绿色那套格式）。
  不清掉的话，你后面加的两个 sink 会**和它叠加**——每条日志打印两遍。
- 【验】写完后打印一条，只出现一次 = 对了；出现两次 = 忘了 remove

---

#### 函数体第 2 段 · 控制台 sink

- 【写】
  ```python
      logger.add(
          sys.stderr,
          level=level,
          format="<green>{time:HH:mm:ss}</green> | <level>{level: <8}</level> | {message}",
          colorize=True,
      )
  ```
- 【讲】四个参数逐个说：
  - `sys.stderr` —— sink（输出目标）。日志走 stderr 是惯例，
    这样 `python xxx.py > out.txt` 不会把日志混进正常输出
  - `level=level` —— 低于这个级别的不显示（DEBUG < INFO < WARNING < ERROR）
  - `format` —— 用尖括号包起来的是颜色标记，`{time}`/`{level}`/`{message}` 是占位符
  - `colorize=True` —— 开启颜色
- 【验】
  ```powershell
  uv run python -c "from kantoku.config.logging_setup import setup_logging; setup_logging(); from loguru import logger; logger.info('控制台测试')"
  ```
  → 看到一行带颜色的 `HH:MM:SS | INFO     | 控制台测试`

---

#### 函数体第 3 段 · 文件 sink（全量 DEBUG）

- 【写】
  ```python
      LOG_DIR.mkdir(parents=True, exist_ok=True)
      logger.add(
          LOG_DIR / "kantoku_{time}.log",
          level="DEBUG",
          format="{time:YYYY-MM-DD HH:mm:ss} | {level: <8} | {name}:{line} | {message}",
          rotation="10 MB",
          retention="7 days",
          encoding="utf-8",
      )
  ```
- 【讲】新增的四个参数：
  - `mkdir(parents=True, exist_ok=True)` —— **目录不存在就建；已存在不报错**。
    没有这句，第一次运行会因为 `data/logs` 不存在而崩
  - `rotation="10 MB"` —— 单个文件超过 10MB 就自动切新的（防止一个文件几十 GB）
  - `retention="7 days"` —— 只保留 7 天，自动删老的（磁盘不会被吃光）
  - `encoding="utf-8"` —— **Windows 必加**，否则中文全是乱码
  - 文件名里的 `{time}` —— loguru 会自动替换成时间戳，所以每次运行是新文件
- 【验】
  ```powershell
  uv run python -c "from kantoku.config.logging_setup import setup_logging; setup_logging(); from loguru import logger; logger.debug('这条只应该在文件里'); logger.info('控制台和文件都有')"
  Get-ChildItem data\logs
  ```
  → `data\logs\` 下出现 `kantoku_xxx.log`，打开能看到 `这条只应该在文件里`；
  但**控制台上没显示它**（因为控制台是 INFO 级别）——这就证明双通道生效了

---

#### 接配置 · level 从 settings 读

- 【写】把函数签名改成可选，内部读配置：
  ```python
  def setup_logging(level: str | None = None) -> None:
      if level is None:
          from .settings import get_settings  # 函数内导入，避免模块加载时就触发配置读取

          level = get_settings().app.log_level
      ...
  ```
- 【讲】为什么 `get_settings()` 要放在**函数里面** import？
  如果在文件顶部就 import，`logging_setup` 一被加载就会去读 yaml——
  万一那时配置还没准备好，整个包都 import 失败。**延迟导入 = 更安全**。
- 【验】把 `settings.yaml` 的 `log_level` 改成 `DEBUG`，重启后控制台也能看到 debug 日志

### 1.5 `core/tracing.py` 埋点（步骤 7）

**知识 3 分钟**

Tracing = 每次调用留一条记录。为什么 W1 就要有？因为 **W8 的成本/成功率/延迟报告全靠查这张表**，  
等到 W8 再补，前面的数据已经永远丢了——这是全项目最容易烂尾的隐性依赖。

**契约**

```python
@dataclass
class Trace:
    ts: str; kind: str; model: str | None
    in_tokens: int; out_tokens: int; latency_ms: int
    cost_cny: float; ok: bool; shot_no: int | None; error: str | None

def init_trace_table(db_path: str) -> None: ...     # 建表（幂等）
def write_trace(t: Trace) -> None: ...              # 落一条
def recent_traces(limit: int = 50) -> list[Trace]: ...
```

**分步 + 自检**

| 步 | 做什么                                             | 自检                                       |
| - | ----------------------------------------------- | ---------------------------------------- |
| 1 | `init_trace_table`：`CREATE TABLE IF NOT EXISTS` | 跑两次不报错（幂等）                               |
| 2 | `write_trace`：参数化 SQL 插入                        | 插一条后用 sqlite 命令行能查到                      |
| 3 | 在 `core/llm.py` 的 TODO 处调用它                     | 调一次 LLM，`select count(*) from trace` = 1 |
| 4 | `recent_traces` 倒序取 N 条                         | CLI 里能打印最近几条                             |

**掉坑提示**

- 建表要用 `IF NOT EXISTS`；连接用完要 `close()`
- `shot_no` 现在是 `None`（W2 才有镜号），字段先留着
- 失败的调用**也要记**（`ok=False`），否则成功率算出来永远是 100%

**过关自测**：`ok=False` 的调用为什么要记？不记会怎样？

### 1.6 `schemas/storyboard.py` 数据契约（步骤 5）

**知识 3 分钟**

Pydantic 在这里有三个用途：① 校验 LLM 返回的 JSON；② `model_dump_json()` 当 schema 样例给 LLM 看；  
③ 作为落库前的统一数据结构。**字段名必须和 `docs/10` 一致**，否则后面到处写转换。

**契约**（字段不许改）

```python
class Shot(BaseModel):
    shot_no: int
    desc: str
    dialogue: str = ""
    camera: str
    duration_s: int
    characters: list[str]

class Storyboard(BaseModel):
    episode: str
    shots: list[Shot]

def parse_storyboard(raw: str) -> Storyboard: ...   # 失败抛 SchemaError 且带原文
```

**分步 + 自检**

| 步 | 做什么                                                      | 自检                             |
| - | -------------------------------------------------------- | ------------------------------ |
| 1 | 写 `Shot` / `Storyboard`，字段与上面完全一致                        | 造一个合法 JSON 能解析                 |
| 2 | `parse_storyboard`：捕获 `ValidationError` 转 `SchemaError`  | 传 `{"bad": 1}` → 报错信息里有原始 JSON |
| 3 | 造一个 `EXAMPLE_SHOT_JSON`（`model_dump_json(indent=2)` 的产物） | 打印出来能直接塞进 prompt               |
| 4 | 单测：成功用例 + 失败用例各一个                                        | `pytest` 2 passed              |

**掉坑提示**

- `model_validate_json()` 是 v2 的入口，别用 v1 的 `parse_raw`
- 失败信息里**必须包含原始返回**——这是排查的唯一线索

**过关自测**：为什么失败时要打印原始返回，而不是只打印"解析失败"？

### 1.7 `shells/cli.py` 命令行外壳（步骤 8）

**知识 3 分钟**

这是**可插拔交互层**的第一层（W1 CLI → W10 可选 VTuber）。内核必须能在没有它的情况下跑  
（headless），所以 CLI 里**不许写业务逻辑**，只做"读一行 → 调 chat → 打印"。

**契约**

```python
def main() -> None:     # while True 循环，输入 exit/quit 退出
```

**分步 + 自检**

| 步 | 做什么                                                    | 自检                                    |
| - | ------------------------------------------------------ | ------------------------------------- |
| 1 | `while True` + `input("监督酱 > ")`                       | 能打字能回显                                |
| 2 | 调 `chat([{"role": "user", ...}])`，打印 `message.content` | 第一次真实对话成功                             |
| 3 | 退出词处理：`exit` / `quit` / `Ctrl+C`                       | 三种都能干净退出                              |
| 4 | 打印 trace 摘要（延迟/token/费用）                               | 每轮结束看到一行 `[trace]`                    |
| 5 | `python -m kantoku.shells.cli` 能启动                     | `uv run python -m kantoku.shells.cli` |

**掉坑提示**

- 需要 `shells/__main__.py` 或 `if __name__ == "__main__": main()`
- Windows 终端中文乱码 → 启动时 `PYTHONIOENCODING=utf-8`

**过关自测**：把 CLI 删掉，你的内核还能跑吗？（能 → 说明分层对了）
