## §1 · 一次完整使用：从头走一遍（先看这个）

**场景**：你接了一单，剧本《雨夜便利店》第 3 集，800 字，要出 20 镜静帧。

> 下面每一步都标注了「**谁在做**」和「**用到哪个知识点**」。
> 你现在只需要看懂流程，不需要知道怎么实现。

### Step 0 · 建项目和角色卡

你在 CLI 里建项目，录入 2 个角色卡：

```
小雨：17岁便利店店员，黑色齐耳短发，红色围裙，圆脸，眼神困倦
老陈：50岁常客，灰色夹克，秃顶，戴老花镜
```

- **存到哪**：SQLite `persona` 表
- **为什么要有它**：后面每一镜的生图 prompt 都从这里取特征词，这是"人物一致性"的根
- **什么时候做**：W3（K1）

---

### Step 1 · 分镜生成 —— 你说一句话，得到 20 镜表格

你说：**"监督酱，帮我把这段剧本拆成 20 镜。"**

系统内部发生了什么（这是 K2 Function Calling 的完整链路）：

```
你的话 + 工具说明书
        ↓  送给 LLM
LLM 决定："我要调用 generate_storyboard 工具，参数是这段剧本"
        ↓  返回一段 JSON（不是人话）
你的代码解析 JSON → 认出是"要调用分镜工具"
        ↓  真正执行函数
得到 20 镜结构 → 存进数据库 → 把结果再喂回 LLM
        ↓
LLM 用人话回你："拆好了，20 镜，预计 3 分 20 秒"
```

**产出长这样**（这就是后面所有步骤的燃料）：

```json
{
  "shot_no": 7,
  "desc": "小雨在货架前整理泡面，抬头看向门口",
  "dialogue": "欢迎光临……咦？",
  "camera": "中景，固定机位，轻微推近",
  "duration_s": 8,
  "characters": ["小雨"]
}
```

- **知识点**：K2 Function Calling（**核心**）+ K1 结构化输出 + K4 评测集
- **什么时候做**：W2
- **做完能演示什么**：贴一段剧本进去，终端打印出 20 行分镜表

---

### Step 2 · 上下文裁剪 + 生成生图 prompt —— 角色不崩的关键

**问题**：20 镜，每镜都要生成 prompt。笨办法是把全部 20 镜 + 全部角色卡一股脑塞给 LLM —— 又贵又会让角色特征互相污染。

**做法**（这是 K3 Context Engineering）：生成第 7 镜时，**只喂这三样**：

1. 第 7 镜自己的描述
2. 第 7 镜出现的角色（只有"小雨"）的卡片 —— **老陈的卡不喂**
3. 前 2 镜的画面描述（保证连续性）—— **不是前 19 镜**

**产出长这样**：

```
1girl, black bob hair, red apron, round face, sleepy eyes,
convenience store shelf, arranging instant noodles,
looking up toward entrance, medium shot, anime style,
<风格统一后缀>
```

前 3 个标签来自角色卡（保证一致性），中间来自分镜描述，最后是全局风格（保证画风统一）。

- **知识点**：K3 Context Engineering
- **什么时候做**：W3
- **做完能演示什么**：打印"裁剪前 3200 token → 裁剪后 640 token"，以及同一角色 5 镜的 prompt

> **这就是你简历上"上下文工程"那条**：不是写更好的提示词，是**决定什么不该进窗口**。

---

### Step 3 · 出图 + 扣钱 —— 成本治理

每一镜出图前的固定动作：

```
reserve(预估 ¥0.15)   ← 先占位，超预算直接拒绝
        ↓
调用生图 API（超时 60s，失败退避重试 2 次）
        ↓
settle(实际 ¥0.15)    ← 多退少补
        ↓
台账写一行：时间 / 镜号 / 预估 / 实际 / 模型
```

超预算时它不是默默失败，而是**说出来**：

> "今天额度只剩 ¥0.8 了，这镜要 ¥0.15，出完就没了。要出吗？"

- **知识点**：K6 成本治理（无视频，按 01 §5 实现）+ K11 asyncio（增强，并发出图）
- **什么时候做**：W4
- **做完能演示什么**：一键出 10 张 + 台账表格 + 故意把额度调低演示拒绝

---

### Step 4 · VLM 质检 —— 让模型看图挑毛病

每张图生成后，把图丢给视觉模型，要求它**只输出 JSON**（不许说废话）：

```json
{
  "broken_hands": false,
  "watermark": false,
  "composition_ok": true,
  "persona_consistency": 4,
  "reason": "发色与围裙与角色卡一致，但眼神偏清醒"
}
```

- 前 3 项是**二元判定**（是/否）—— 稳定、可验收
- 第 4 项是**5 分制打分** —— 主观，用来排序"哪些最该重做"

不合格的进**重做队列**，你确认后才重出（人在回路）。

- **知识点**：K10 VLM + K4 评测（先建 30 张标注集跑基线）
- **什么时候做**：W5
- **做完能演示什么**："这 10 张里 7 张合格，3 张建议重做，理由是……"

---

### Step 5 · 归档打标

图片自动重命名 + 入库，之后能按集数 / 镜号 / 角色检索：

```
outputs/ep03/shots/ep03_shot07_v2.png     ← 第3集第7镜第2版
```

- **知识点**：K5（检索部分）
- **什么时候做**：W5

---

### Step 6 · 记忆与检索

你问：**"上一集小雨穿的什么？"**

系统走**混合检索**（FTS5 关键词 + sqlite-vec 向量），从人设卡库和素材库里找，答：

> "上集小雨是红色围裙 + 白色内搭，与本集一致。"

- **知识点**：K5 SQLite + 混合检索
- **什么时候做**：W6
- **做完能演示什么**：**关掉程序再打开**，它还记得（这叫 checkpoint / 持久化）

---

### Step 7 · 状态机 —— 中断了能接着跑

上面 Step 1–6 是一条链。你关电脑、API 抽风、余额不够……都会断。

状态机把这条链显式化：`拆镜 → 出图 → 质检 → 归档`，每走一步存个**断点**。下次启动从断点继续，不重跑。

三个地方**必须停下来问你**（人在回路 HITL）：

| 节点 | 问什么 |
|---|---|
| 批量出图前 | "20 镜预计 ¥3.0，今天额度 ¥5，出吗？" |
| 超预算时 | "只剩 ¥0.8 了，还出吗？" |
| 重做前 | "3 张建议重做，重做要多花 ¥0.45，要重做吗？" |

- **知识点**：K8 状态机 / LangGraph 概念
- **什么时候做**：W7
- **做完能演示什么**：跑到一半强制关掉 → 重启 → 接着跑完

---

### Step 8 · MCP —— 同一批工具，换个地方也能用

W1–W7 你写了 6 个工具（分镜、prompt、出图、质检、归档、台账）。
W8 给它们套一层 MCP 协议，**不用重写**，于是：

你在 Claude Code / Cursor 里直接说：

> "把 ep03 的分镜导出成 Markdown 表格"

它就能调用你的工具。

- **知识点**：K7 MCP
- **什么时候做**：W8
- **做完能演示什么**：在外部客户端里调用你自己写的工具

---

### Step 9 · 交付报告 —— 简历上的数字从这里来

一集做完，自动生成：

```
《雨夜便利店》EP3  交付报告
─────────────────────────
工时       6.2h  →  3.8h   (-39%)
生图成本          ¥12.30
废片率            18%
人工返工          3 张
质检通过率        82%
─────────────────────────
```

- **什么时候做**：W9

## §3 · 反向索引：学这个知识点 → 实现哪个功能

| 知识点 | 你学完立刻要写的东西 | 它撑起的功能 | 不学会怎样 |
|---|---|---|---|
| K0 uv/pytest | `uv sync` 跑通空测试 | 整个工具链 | 环境一团糟，天天在装包 |
| K1 API+结构化输出 | `core/llm.py` | 所有模型调用 | 后面每个模块都在救解析的火 |
| **K2 Function Calling** | `agent/loop.py` | **AI 会自己决定调哪个工具** | **项目变成普通 chatbot，彻底失去 Agent 属性** |
| K3 Context Engineering | `agent/context.py` | 角色不崩 + 省钱 | 20 镜互相污染，成本翻倍 |
| K4 Eval | `evals/*.jsonl` | 证明改动是好是坏 | 改 prompt 全靠感觉，无法量化 |
| K5 SQLite+检索 | `memory/` | 重启还记得、能搜素材 | 每次重开都失忆 |
| K6 成本治理 | `core/budget.py` | 不烧钱 | 一觉醒来欠费 |
| K7 MCP | `mcp_server.py` | 工具复用给外部客户端 | 少一个 JD 高频关键词 |
| K8 状态机 | `agent/graph.py` | 可中断可恢复 | 跑到一半崩了只能重来 |
| K9 Tracing | `core/tracing.py` | 所有报告的源头 | 最后补不出来，报告全靠编 |
| K10 VLM | `perception/qc.py` | 自动挑废片 | 人工一张张看，工时压不下来 |
| K11 asyncio | 批量出图并发 | 出图更快 | 慢，但不致命 |
| K13 漫剧流程 | 05 表 | 需求来源 | 做出来的工具没人用 |

## §4 · 如果只能记住一张图

```
你的一句话
    │
    ▼
┌─ shells/ ────────────────────────────────────────┐
│  CLI（W1）· Gradio（可选）· VTuber（W10 可选）      │  ← 只是入口，随便换
└───────────────────┬───────────────────────────────┘
                    ▼
┌─ agent/ ─────────────────────────────────────────┐
│  loop.py   手写工具调用循环（心脏）      K2        │
│  context.py 按镜号裁剪上下文             K3        │
│  graph.py  状态机 + checkpoint（可中断） K8        │
└───────────────────┬───────────────────────────────┘
                    ▼
┌─ tools/ ─────────────────────────────────────────┐
│  ①分镜 ②prompt工厂 ③出图 ④质检 ⑤归档 ⑥台账        │  ← 六个工具，一次实现
└───────────────────┬───────────────────────────────┘
                    ▼
┌─ core/ ──────────────────────────────────────────┐
│  llm.py（唯一出口）· tracing.py（记账）            │
│  budget.py（闸门）                                │
└───────────────────┬───────────────────────────────┘
                    ▼
┌─ data/ ──────────────────────────────────────────┐
│  SQLite：shot / persona / asset / qc / ledger /   │
│          trace / checkpoint                      │
└──────────────────────────────────────────────────┘

旁路：mcp_server.py ── 同一批 tools，换个协议给外部用（W8）
      scripts/run_eval.py ── 从 eval 集生成报告（W2 起）
```

**三条记住就不会迷路**：
1. **所有模型调用只走 `core/llm.py` 一个出口** —— 超时、重试、记 trace 都在那，别到处写。
2. **工具是独立的纯函数** —— 不依赖 agent，所以能同时给你自己的 loop 和 MCP 用。
3. **数据全在 SQLite 一张库里** —— 台账、trace、质检、记忆都从这出，所有报告才有数可依。

## §5 · 常见困惑速答

| 困惑 | 答案 |
|---|---|
| Agent 和普通聊天机器人区别在哪？ | 在 Step 1：它自己**决定**要不要调工具、调哪个、传什么参数。K2 就是学这个 |
| 为什么不直接调 API 写死流程？ | 那样是脚本不是 Agent。JD 要的是"任务规划 + 工具调用"的决策能力 |
| 底座（VTuber）到底还做不做？ | **主线不用，W10 可选，砍掉不扣分**。详见 §6 |
| Context Engineering 和 Prompt 工程区别？ | Prompt 工程琢磨"怎么说"；上下文工程琢磨"给什么"。后者决定成本和一致性 |
| 状态机和我手写 if-else 有什么区别？ | 状态机把"当前在哪一步"显式存下来，所以能中断恢复。if-else 崩了就得重来 |
| 为什么要先建标注集再调模型？ | 先有 30 张人工标注，才知道模型判得准不准。**先定 85% 再倒逼模型 = 卡死一周** |
| 这项目最值钱的模块是哪个？ | **预算治理 + 评测集**。这两样 90% 的求职者没有 |

## §6 · 关于 Open-LLM-VTuber 的最终决定

### 结论：主线不用，W10 可选，砍掉不扣分

| 阶段 | 用不用 | 说明 |
|---|---|---|
| W1–W9 | **完全不用** | 主线全程 headless：CLI 打字进出 |
| W10 | **可选** | 只在"进度正常 + 还有余力"时才碰 |
| 砍掉 | **不扣分** | 不影响任何里程碑验收，不影响简历竞争力 |

### 为什么这么定（事实依据，2026-09 核实）

1. **它正在 v2.0 全量重写，v1 已 feature-frozen**。官方 README 原话：
   "v2.0 — a complete rewrite of the codebase… refrain from opening new issues or PRs
   for feature requests on v1."（只修 bug，不接新需求）
2. **长期记忆功能已被临时移除**，而"记忆"恰恰是你 M5 要自己做的东西。
3. **Windows 部署是著名的时间黑洞**：ASR（sherpa-onnx / FunASR）+ ffmpeg + 回声消除 +
   Live2D 模型，新手实际 1.5–2 周很常见，而它和你的简历核心资产（工具调用 / 预算 /
   质检 / 评测）**毫无关系**。

> 一句话：**它是个"说话的壳"，你的价值在壳后面的大脑。先造大脑。**

### 但是——"有音色的二次元人设"这个目标不放弃

**底座 ≠ 音色**。这三件事可以分开拿，不用装整套：

| 想要的效果 | 真实依赖 | 成本 |
|---|---|---|
| 会打字回你 | `shells/cli.py` | W1 就有 |
| 会说话（普通音色） | Edge TTS（免费、免训练、pip 装） | 几十分钟 |
| 会说话（角色音色） | GPT-SoVITS（**独立项目，不依赖底座**） | W10 可选 |
| 有 Live2D 形象 | 才需要 Open-LLM-VTuber | W10 可选，且可放弃 |

**推荐路径**：W1 先 CLI → 想听声音就单独接 Edge TTS（不碰底座）→ 真有空再谈 GPT-SoVITS。

### W10 的决策树（到时照着判断，现在不用想）

```
W9 结束时 ── 进度落后？── 是 → 砍掉，永不接，去写 README
                │
                否
                ↓
     求职方向偏"多模态 / 交互 / 端侧"？
        否 → 砍掉，把时间用来打磨演示视频
        是 → 给它 1 天。1 天跑不通？
                是 → 放弃，改用 Gradio 做个 Web 界面（1 小时）
                否 → 接上，录进 W10 演示
```

### 三个可以"白嫖"它的思路（不用装它的代码）

1. **`conf.yaml` 驱动一切**——它所有后端（LLM / ASR / TTS）都靠改配置字符串切换，不写代码。
   你的 `config/settings.yaml` 已经是这个思路，保持。
2. **角色卡字段设计**——它的 `character_config`（人设 / 语气 / Live2D 模型名）可以参考，
   帮你设计 W3 的人设卡结构。
3. **它支持 MCP**（仓库里有 `mcp_servers.json`）——意味着你 W8 写的 MCP Server，
   将来如果真接底座，可以直接挂上去，不用重写。

### 简历上怎么写（不提它也能拿到分）

❌ 不要写："基于 Open-LLM-VTuber 二次开发"

✅ 要这么写：

> "设计可插拔交互层（`InteractionShell`）：主线以 CLI 驱动，交互层与 Agent 内核解耦，
> 可平滑替换为语音 / Live2D 外壳。"

**这句比"用了某某开源项目"强得多**——它证明的是你做了架构决策，而不是你会装环境。
