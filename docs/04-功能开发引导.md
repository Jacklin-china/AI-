### 2.1 `config/errors.py` 异常树 ✅ 已完成

> **复习用**：这一节你已经写完了。卡住时回来看「知识 3 分钟」。

**知识 3 分钟**

为什么要有异常树？因为不同错误的**处理方式不同**：

- `BudgetError` 必须**告诉用户**（不默默失败，这是 K6 考点）
- `SchemaError` 必须**带原始返回**（否则线上无法排查）
- `LLMError` 可以**重试**

如果全用 `raise Exception("xxx")`，调用方没法区分，只能一把兜住——那就失去了精细处理的能力。

| 你项目里会遇到的失败 | 想要的处理方式 | 所以叫 |
|---|---|---|
| 密钥没配 / yaml 字段缺 | 立刻停，告诉用户去配 | `ConfigError` |
| 调模型超时、被限流 | 等一下重试 | `LLMError` |
| 模型返回的 JSON 不合格式 | 打印原始返回，人工排查 | `SchemaError` |
| 今天的钱花超了 | **必须告诉用户**，不许偷偷跳过 | `BudgetError` |

**契约**

```python
class KantokuError(Exception):
    def __init__(self, message: str, *, detail: str | None = None) -> None: ...

class ConfigError(KantokuError): ...    # 配置缺失/密钥未设
class LLMError(KantokuError): ...       # 调用失败（可重试）
class SchemaError(KantokuError): ...    # 解析失败（必须带原始返回）
class BudgetError(KantokuError): ...    # 超预算（必须明确拒绝）
```

**关键知识点回顾**

| 行 | 写了什么 | 为什么 |
|---|---|---|
| `class KantokuError(Exception)` | 继承 | 读作"`KantokuError` **是一种** `Exception`"，继承后才能被 raise / except |
| `def __init__(self, message: str, *, detail: str \| None = None)` | `*` 的作用 | 它后面的参数**必须写名字**传：`KantokuError("a", detail="b")` ✅ ／ `KantokuError("a", "b")` ❌ |
| `super().__init__(message)` | 交给父类 | **实测真相**：现代 Python 不写这行 `str(e)` 也不会空（网上"不写就变空"是过时说法）。还要写是因为 ①明确 ②安全（多重继承）③一致（`args` 与 `message` 同步） |
| `self.message = message` / `self.detail = detail` | 存到对象上 | 后面 `core/tracing.py` 要读 `e.message` 和 `e.detail` 写进数据库 |
| `def __str__` | 控制报错长什么样 | 有 `detail` 就拼 `message｜detail`，没有就只返回 `message` |

> **为什么不是 `super().__init__(detail)`？**
> 实测 `Exception("超时", "重试2次")` 的 `str()` 会变成 `('超时', '重试2次')`——**元组形式，很难看**。
> 父类只认"一条主消息"，`detail` 是我们自己扩展的字段，所以自己存、自己拼，显示完全可控。

**自检（已完成，可复查）**

```powershell
uv run python -c "from kantoku.config.errors import *; print(str(KantokuError('a', detail='b'))); print([isinstance(c('t'), KantokuError) for c in (ConfigError, LLMError, SchemaError, BudgetError)])"
```
→ `a｜b` 和 `[True, True, True, True]`

**过关自测（三问）**
1. `except KantokuError` 为什么能兜住 `LLMError`？（答：子类属于父类，`isinstance` 为 True）
2. 为什么超预算要单独 `BudgetError`，不能复用 `LLMError`？（答：处理动作不同——一个要重试，一个必须告知用户）
3. 为什么解析失败要打印原始返回？

### 2.2 `config/settings.py` 配置入口 ⏳ 进行中

#### 🎯 有什么用
所有模型名 / URL / 超时 / 预算的**唯一读取入口**。W8 换模型、W4 换生图供应商能不能"只改一行 yaml"就完成，全靠这个模块。

#### 第 0 步 · 先想清楚要管哪些东西（写之前 1 分钟）

| 要管的东西 | 放哪 | 为什么 |
|---|---|---|
| 模型地址 / 模型名 / 超时 / 重试 | `config/settings.yaml` | 能提交 git，换供应商只改这里 |
| **密钥** | `.env`（环境变量） | **绝不能进 git**，泄露 = 别人刷你的钱 |
| 每日预算 / 数据库路径 | `config/settings.yaml` | 同上 |

> 一句话原则：**结构进 yaml，秘密进环境变量。**
> `settings.yaml` 是你自己从 `settings.example.yaml` 复制出来的（被 git 忽略）；
> `example` 是模板，是配置结构的唯一事实来源，要提交。

#### 第 1–7 行 · 导入

- 【写】

  ```python
  import os
  from functools import lru_cache
  from pathlib import Path
  ```

#### 然后 · 总入口 Settings

- 【写】
  ```python
  class Settings(BaseSettings):
      """配置总入口。yaml 提供结构，环境变量提供密钥。"""

      model_config = SettingsConfigDict(env_prefix="KANTOKU_", extra="ignore")

      app: AppSettings = AppSettings()
      llm: LlmSettings = LlmSettings()
      budget: BudgetSettings = BudgetSettings()
      storage: StorageSettings = StorageSettings()
  ```

- 【讲】
  - `env_prefix="KANTOKU_"` —— 允许用 `KANTOKU_XXX` 环境变量覆盖

  - 每个字段给默认值 → `Settings()` 永远能创建，**不会因缺配置而 import 崩溃**
  - ⚠️ 如果用 `BaseSettings` 就要 `from pydantic_settings import BaseSettings, SettingsConfigDict`；
    只用 `BaseModel` 也完全可以（本项目 yaml 才是配置源）——**选一个别混**

#### 然后 · `_require_env()`：密钥缺失就明确报错

- 【写】
  ```python
  def _require_env(name: str) -> str:
      value = os.environ.get(name)
      if not value:
          raise ConfigError(
              f"环境变量 {name} 未设置",
              detail="请在项目根目录的 .env 里配置，或先执行："
              f'$env:{name}="你的密钥"（PowerShell）',
          )
      return value
  ```
- 【讲】**这里用上了上一节的 `ConfigError` 和它的 `detail` 参数**。
  为什么不用 `raise Exception`？因为调用方能 `except ConfigError` 精确捕获，给用户一句"去配 .env"的友好提示，而不是一堆看不懂的 traceback。
- 【验】
  ```powershell
  uv run python -c "from kantoku.config.settings import _require_env; _require_env('NOT_EXIST_KEY')"
  ```
  → 应看到 `环境变量 NOT_EXIST_KEY 未设置｜请在项目根目录的 .env 里配置...`

> 之前 `chat_api_key()` 里 `_require_env` 爆红，就是因为这个函数还没写。**写完这一段，红线消失。**

#### 然后 · `_read_yaml()`：读文件 + 兜底

- 【写】
  ```python
  def _read_yaml() -> dict:
      path = CONFIG_PATH if CONFIG_PATH.exists() else EXAMPLE_PATH
      if not path.exists():
          raise ConfigError("找不到配置文件", detail=f"期望路径：{CONFIG_PATH}")
      with path.open(encoding="utf-8") as f:
          return yaml.safe_load(f) or {}
  ```
- 【讲】两个细节：
  - **兜底**：没有 `settings.yaml`（还没复制）就退回 example → 别人 clone 你的仓库也能跑
  - `encoding="utf-8"` → yaml 有中文注释，不加会乱码/报错
- 【验】`uv run python -c "from kantoku.config.settings import _read_yaml; print(list(_read_yaml().keys()))"`
  → `['app', 'llm', 'budget', 'storage', 'vtuber']`

- 【讲】
  - `**raw.get("llm", {})` —— 把字典拆成关键字参数（就是 K1 视频里那个 `**`）
  - **`yaml 覆盖类默认值`**：`LlmSettings(**{...})` 就是把 yaml 的值传进去，覆盖类里写的默认值。
    所以**换模型只改 yaml，不要改代码里的默认值**
  - `@lru_cache(maxsize=1)` —— 第一次调用读盘，之后返回缓存的同一份。
    **副作用：改了 yaml 要重启进程才生效**（别到时候以为改了没反应）
- 【验】


### 2.3 `config/logging_setup.py` 日志（下一个要写的）

#### 🎯 有什么用
W8 的 trace 报告、W4 的成本台账都靠日志留证据。**终端一关就没的东西等于没发生。**
这是所有生产级项目的基本配置，也是面试官判断"是不是玩具项目"的细节之一。

#### 第 0 步 · 先想清楚为什么要有两个出口

| 出口 | 给谁看 | 级别 | 特点 |
|---|---|---|---|
| **控制台** | 正在操作的你 | INFO 以上 | 带颜色、简洁 |
| **文件** | 出事之后排查的你 | DEBUG 全量 | 滚动切分、保留 7 天 |

只留控制台 → 关掉终端就没了；只留文件 → 平时看不到进度。这叫**双通道**。

#### 第 1–4 行 · 导入

- 【写】
  ```python
  from __future__ import annotations

  import sys
  from pathlib import Path

  from loguru import logger
  ```
- 【讲】
  - `sys` —— 拿 `sys.stderr`（控制台输出目标）
  - `Path` —— 拼日志目录
  - `logger`（loguru）—— 和标准库 `logging` 最大区别：**它是现成的全局对象**，
    不需要 `logging.getLogger(__name__)` 那套，import 就能用
- 【验】无

#### 第 6–8 行 · 目录与函数签名

- 【写】
  ```python
  LOG_DIR = Path("data") / "logs"


  def setup_logging(level: str | None = None) -> None:
  ```
- 【讲】`Path("data") / "logs"` 而不是 `"data/logs"`：Path 自动处理 Windows 反斜杠。
  签名里 `level: str | None = None` —— 不传就去读配置（见下面"接配置"）。

#### 函数体第 1 行 · 清掉默认输出 ⚠️ 最容易忘

- 【写】（缩进 4 空格）
  ```python
      logger.remove()
  ```
- 【讲】loguru **默认自带一个输出到 stderr 的 sink**（绿色那套格式）。
  不清掉的话，你后面加的两个 sink 会**和它叠加**——每条日志打印两遍。
- 【验】写完后打印一条，只出现一次 = 对了；出现两次 = 忘了 remove

#### 函数体第 2 段 · 控制台 sink

- 【写】
  ```python
      logger.add(
          sys.stderr,
          level=level,
          format="<green>{time:HH:mm:ss}</green> | <level>{level: <8}</level> | {message}",
          colorize=True,
      )
  ```
- 【讲】
  - `sys.stderr` —— sink（输出目标）。日志走 stderr 是惯例，这样 `python x.py > out.txt` 不会把日志混进正常输出
  - `level=level` —— 低于此级别不显示（DEBUG < INFO < WARNING < ERROR）
  - `format` —— 尖括号里是颜色标记，`{time}`/`{level}`/`{message}` 是占位符
- 【验】
  ```powershell
  uv run python -c "from kantoku.config.logging_setup import setup_logging; setup_logging(); from loguru import logger; logger.info('控制台测试')"
  ```
  → 看到一行带颜色的 `HH:MM:SS | INFO     | 控制台测试`

#### 函数体第 3 段 · 文件 sink（全量 DEBUG）

- 【写】
  ```python
      LOG_DIR.mkdir(parents=True, exist_ok=True)
      logger.add(
          LOG_DIR / "kantoku_{time}.log",
          level="DEBUG",
          format="{time:YYYY-MM-DD HH:mm:ss} | {level: <8} | {name}:{line} | {message}",
          rotation="10 MB",
          retention="7 days",
          encoding="utf-8",
      )
  ```
- 【讲】
  - `mkdir(parents=True, exist_ok=True)` —— **不存在就建；已存在不报错**。没有这句，第一次运行会因 `data/logs` 不存在而崩
  - `rotation="10 MB"` —— 单文件超 10MB 自动切新的
  - `retention="7 days"` —— 只保留 7 天，自动删老的
  - `encoding="utf-8"` —— **Windows 必加**，否则中文全乱码
  - `{time}` —— loguru 自动替换成时间戳
- 【验】
  ```powershell
  uv run python -c "from kantoku.config.logging_setup import setup_logging; setup_logging(); from loguru import logger; logger.debug('这条只应该在文件里'); logger.info('控制台和文件都有')"
  Get-ChildItem data\logs
  ```
  → `data\logs\` 下出现 `kantoku_xxx.log`，打开能看到"这条只应该在文件里"；
  但**控制台上没显示它**——这就证明双通道生效了

#### 接配置 · level 从 settings 读

- 【写】
  ```python
      if level is None:
          from .settings import get_settings  # 函数内导入

          level = get_settings().app.log_level
  ```
- 【讲】为什么 `get_settings()` 放在**函数里面** import？
  顶部 import 的话，`logging_setup` 一被加载就会读 yaml——万一配置还没准备好，整个包 import 失败。**延迟导入 = 更安全**。
- 【验】把 `settings.yaml` 的 `log_level` 改成 `DEBUG`，重启后控制台也能看到 debug 日志

#### 收尾

```powershell
uv run ruff check .; if ($?) { uv run pytest }
```

**掉坑提示**
- 日志里别用 f-string：写 `logger.info("x={}", x)` 而不是 `logger.info(f"x={x}")`——前者惰性，被过滤时不执行格式化
- Windows PowerShell 颜色可能显示成乱码字符 → 不影响文件，介意就 `colorize=False`
- `data/` 已被 `.gitignore` 忽略（正确），日志不会误提交

### 2.4 `core/llm.py` LLM 客户端

#### 🎯 有什么用
**所有模型调用的唯一出口。** 超时、重试、降级、记 trace 全在这里。
别处一律不许直接 `OpenAI(...)` —— 否则换供应商要改 N 处，trace 也会漏。

**知识 3 分钟**

- OpenAI SDK 的 `OpenAI(base_url=..., api_key=...)` 能接任何 OpenAI 兼容端点（豆包 / 智谱 / 混元都是）
- `chat.completions.create()` 返回 3 层壳：`response.choices[0].message`
- **这次要返回 `message` 对象而不是 `.content`** —— 因为 W2 要读 `message.tool_calls`
- 超时重试不是锦上添花：网络抖动和限流是常态，没有它你的 Agent 会随机崩

**契约**

```python
def chat(
    messages: list[dict],
    *,
    model: str | None = None,         # 默认取 settings.llm.model_chat
    temperature: float | None = None,  # 默认取 settings.llm.temperature
    response_format: dict | None = None,
    tools: list[dict] | None = None,
    timeout_s: int | None = None,
) -> object:                          # 返回 message 对象
    """一次 LLM 调用：超时重试 → 失败转 LLMError → 返回 message。"""
```

**分步 + 自检**

| 步 | 做什么 | 自检方法 |
|---|---|---|
| 1 | 建 client：`OpenAI(base_url=settings.llm.base_url, api_key=settings.llm.chat_api_key())` | 不报错即可（还没发请求） |
| 2 | 最小 `chat()`：只传 model + messages，返回 `.choices[0].message` | 调一次，打印 `message.content` 能出中文 |
| 3 | 加超时：`timeout=settings.llm.timeout_s` | 故意把 timeout 设成 0.001，应抛超时异常 |
| 4 | 加重试：失败退避重试 `settings.llm.retry` 次，**重试前 sleep 递增** | 断网跑一次，看到重试日志 |
| 5 | 异常转化：`except Exception as e: raise LLMError(...) from e` | 填错 key，应看到 `LLMError` 而不是原始 traceback |
| 6 | 预留 trace 钩子（下一步实现）：`# TODO: write_trace(...)` | 有 TODO 注释即可 |
| 7 | 降级位：主力失败且配了 fallback → 用 `fallback_*` 再试一次 | 把主力 model 改成不存在的名字，应自动走降级 |

**掉坑提示**

- 火山方舟的 key 环境变量是 `ARK_API_KEY`，**没填会直接 `ConfigError`**（这正是我们设计的保护）
- `base_url` 末尾带不带 `/v1`？**以控制台给的为准**，错了会 404
- 豆包 turbo 支持 `response_format={"type": "json_object"}`，但 **W2 更推荐用 tools**，json_object 只是兜底
- 返回的 message 里 `tool_calls` 可能是 `None`，W2 判断时要用 `if not msg.tool_calls`

**过关自测（三问）**
1. 为什么这次返回 `message` 而不是 `message.content`？
2. 超时和重试的值从哪来？
3. 主力模型挂了会发生什么？

```python
# agent/loop.py 骨架 —— 不许看资料，闭卷写，写完再对照视频
def run(user_msg: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": user_msg}]
    for step in range(max_steps):
        msg = chat(messages, tools=registry.to_json_schema())
        if not msg.tool_calls:                     # 没有工具调用 = 说人话 = 结束
            return msg.content
        for call in msg.tool_calls:                # 逐个执行工具
            fn = registry.get(call.function.name)
            args = json.loads(call.function.arguments)
            result = fn(**args)                    # ← Pydantic 校验在这里生效
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": json.dumps(result, ensure_ascii=False)})
    raise LLMError("超出最大步数，可能陷入循环")
```

### 📌 今天做什么
一键出 10 张图，每张走 `reserve → 调用 → settle`，台账记账，额度不够时**明确问你**。

### 🎯 这个功能在项目里有什么用

```

   ↓

```

- **简历价值**：成本治理是 JD 加分项，**几乎没人有**。这是你最值钱的两块之一（另一块是评测集）。

### 📺 看什么
**K6 没有视频，也不需要有** —— 这恰恰是你的差异化，按 `01` §5 实现。
*（增强档）* [asyncio 并发](https://www.bilibili.com/video/BV157mFYEEkH/) 30 min，只学 `asyncio.gather` + 信号量。

### 🛠 写什么

| # | 文件 | 关键内容 |
|---|---|---|
| 1 | `tools/image_gen.py` | `gen_image(prompt: str, shot_no: int) -> Path`，超时 60s，失败退避重试 2 次 |
| 2 | `core/budget.py` | `reserve(est)` → 调用 → `settle(actual)`，超限抛 `BudgetError`（**不默默失败**） |
| 3 | `db` 台账表 `ledger` | ts / episode / shot_no / kind / est_cny / actual_cny / model |
| 4 | `shells/cli.py` | 超预算时明确询问，得到 `y` 才放行 |
| 5 | *（增强）* asyncio | `asyncio.gather` + 信号量限流，量化耗时下降 |

### ✅ 验收 / 🛑 止损

- **验收**：分镜表一键出图；台账每张图有记录；超预算被拒绝。
- **🛑 止损**：生图 API 接入 >2 天 → **立即停**，先用本地假图跑通编排与台账。**编排和台账才是资产，API 只是个函数。**
