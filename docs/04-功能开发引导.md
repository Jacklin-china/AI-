### 0.1 每个功能都用同一套“掌握闭环”

目标不是把 AI 给出的代码粘进仓库，而是最后能独立解释、重写、测试和修改。每个功能严格走完八步：

| 步骤 | 先回答什么 | 产出 | 为什么不能跳 |
|---|---|---|---|
| 1. 业务定位 | 它解决哪个真实痛点？不用会损失什么？ | 一句话价值 + 对应指标 | 防止为了技术关键词写无用功能 |
| 2. 数据流定位 | 上游给什么、下游拿什么？ | 输入/输出/副作用清单 | 防止模块边界混乱 |
| 3. 契约设计 | 类型、字段、异常、配置分别是什么？ | 函数签名/Schema/错误表 | 先定边界，避免边写边改 |
| 4. 路径推演 | 正常、非法输入、外部失败、恢复分别怎么走？ | 简短流程图或伪代码 | 生产逻辑主要藏在失败路径里 |
| 5. 微步编码 | 现在只写哪个最小函数或 10–30 行？ | 你亲手完成的一小段代码 | 降低认知负荷，出现错误容易定位 |
| 6. 立即验证 | 最小成功例和最小失败例是什么？ | 定向测试 + 观察结果 | 不是“看起来对”，而是有证据 |
| 7. 闭卷迁移 | 不看答案能否复述，并改一个小需求？ | 口述 + 小改动 + 新测试 | 能修改才说明真正理解 |
| 8. 工程收尾 | 全量检查、演示、记录是否完成？ | ruff/pytest + 演示 + §10 记录 | 防止学会了但项目仍不可交付 |

**AI 每次只能这样引导**：

1. 先解释本步的业务作用、知识点和设计理由；
2. 给签名、伪代码、关键 API 或局部示例，不直接倾倒完整文件；
3. 明确“现在只写哪一小步”和预期观察结果；
4. 等你写完后审查，指出原因并让你自己修；
5. 通过成功/失败测试后，再进入下一小步；
6. 如果你明确要求完整实现，仍要先标出你必须掌握的关键段，并在完成后做闭卷迁移。

**每个微步统一使用下面的通俗讲解模板**：

```text
【本步要解决的麻烦】不用术语，先说真实问题。
【你现在只写】只给当前 10–30 行或一个函数，不泄露后续完整答案。
【逐块拆解】每块代码分别接收什么、做什么、返回/改变什么。
【正式知识点】给通俗概念补上准确术语，方便以后查官方资料。
【为什么这样设计】解释依赖方向、数据流、取舍，以及为什么不选另一个写法。
【常见错误】展示会出什么错、为什么错，不只给“正确答案”。
【马上验证】给可观察的成功与失败用例，并说明预期现象。
【闭卷复述】让你不用代码讲清逻辑。
【迁移小题】改变一个需求，由你同步修改类型、代码和测试。
```

语言要求：先用生活化表达建立直觉，再给准确术语；避免“完美解决”“工业级标准”这类没有边界的绝对评价。代码块必须使用真实语言标签，例如 Python 只能标记为 `python`。

**功能掌握门（五项全部满足才打勾）**：

- [ ] 我能不用代码解释输入、输出、副作用和失败路径。
- [ ] 我能根据签名自己写出核心流程，而不是逐行照抄。
- [ ] 我能为成功和失败路径各写至少一个测试。
- [ ] 我能根据日志定位一个故意制造的错误。
- [ ] 我能修改一个小需求，并同步调整类型、实现和测试。

### 2.1 `config/errors.py` 异常树 ✅ 已完成

> **复习用**：这一节你已经写完了。卡住时回来看「知识 3 分钟」。

**知识 3 分钟**

为什么要有异常树？因为不同错误的**处理方式不同**：

- `BudgetError` 必须**告诉用户**（不默默失败，这是 K6 考点）
- `SchemaError.raw` 必须带原始返回供主动排查；异常文本和日志只显示安全摘要。
- `LLMError` 可以**重试**

如果全用 `raise Exception("xxx")`，调用方没法区分，只能一把兜住——那就失去了精细处理的能力。

| 你项目里会遇到的失败 | 想要的处理方式 | 所以叫 |
|---|---|---|
| 密钥没配 / yaml 字段缺 | 立刻停，告诉用户去配 | `ConfigError` |
| 调模型超时、被限流 | 等一下重试 | `LLMError` |
| 模型返回的 JSON 不合格式 | 显示安全错误摘要，必要时主动检查 `.raw`，不自动记录剧本正文 | `SchemaError` |
| 今天的钱花超了 | **必须告诉用户**，不许偷偷跳过 | `BudgetError` |
| trace 数据库打不开或读写失败 | 保留原业务结果并记错误日志；直接调用时明确报错 | `TracingError` |

**契约**

```python
class KantokuError(Exception):
    def __init__(self, message: str, *, detail: str | None = None) -> None: ...

class ConfigError(KantokuError): ...    # 配置缺失/密钥未设
class LLMError(KantokuError): ...       # 调用失败（可重试）
class SchemaError(KantokuError): ...    # 解析失败（必须带原始返回）
class BudgetError(KantokuError): ...    # 超预算（必须明确拒绝）
class TracingError(KantokuError): ...   # trace 数据库初始化或读写失败
```

**关键知识点回顾**

| 行 | 写了什么 | 为什么 |
|---|---|---|
| `class KantokuError(Exception)` | 继承 | 读作"`KantokuError` **是一种** `Exception`"，继承后才能被 raise / except |
| `def __init__(self, message: str, *, detail: str \| None = None)` | `*` 的作用 | 它后面的参数**必须写名字**传：`KantokuError("a", detail="b")` ✅ ／ `KantokuError("a", "b")` ❌ |
| `super().__init__(message)` | 交给父类 | **实测真相**：现代 Python 不写这行 `str(e)` 也不会空（网上"不写就变空"是过时说法）。还要写是因为 ①明确 ②安全（多重继承）③一致（`args` 与 `message` 同步） |
| `self.message = message` / `self.detail = detail` | 存到对象上 | 后面 `core/tracing.py` 要读 `e.message` 和 `e.detail` 写进数据库 |
| `def __str__` | 控制报错长什么样 | 有 `detail` 就拼 `message｜detail`，没有就只返回 `message` |

> **为什么不是 `super().__init__(detail)`？**
> 实测 `Exception("超时", "重试2次")` 的 `str()` 会变成 `('超时', '重试2次')`——**元组形式，很难看**。
> 父类只认"一条主消息"，`detail` 是我们自己扩展的字段，所以自己存、自己拼，显示完全可控。

**自检（已完成，可复查）**

```powershell
uv run python -c "from kantoku.config.errors import *; print(str(KantokuError('a', detail='b'))); print([isinstance(c('t'), KantokuError) for c in (ConfigError, LLMError, SchemaError, BudgetError)])"
```
→ `a｜b` 和 `[True, True, True, True]`

**过关自测（三问）**
1. `except KantokuError` 为什么能兜住 `LLMError`？（答：子类属于父类，`isinstance` 为 True）
2. 为什么超预算要单独 `BudgetError`，不能复用 `LLMError`？（答：处理动作不同——一个要重试，一个必须告知用户）
3. 为什么解析失败要打印原始返回？

### 2.3 `config/logging_setup.py` 日志（完成 settings 后再写）

> 这一节就是后续所有代码讲解的标准样板：先说它解决什么麻烦，再看局部代码，然后解释知识点、设计逻辑、错误写法和验证方法。

#### 1. 这个功能到底解决什么麻烦

程序运行时会同时面对两种需求：

| 场景 | 需要什么 | 对应出口 |
|---|---|---|
| 你正在操作程序 | 只看当前重要进度，不能被 DEBUG 刷屏 | 控制台：INFO 及以上、简洁、彩色 |
| 程序已经出错 | 回看完整时间、模块、行号和调试细节 | 文件：DEBUG 及以上、按天切分、保留 14 天 |

只打控制台，窗口关闭后证据消失；只写文件，操作时又看不到反馈。因此需要**双通道日志**。日志只能帮助排错，业务指标仍写 trace/ledger，不能把日志文件当数据库。

#### 2. 先看依赖方向，而不是急着写 import

```text
logging_setup.py → settings.py → errors.py
```

这是单向依赖：日志模块读取配置，配置模块只使用异常，不反向导入日志。因此可以正常在文件顶部导入 `ROOT` 和 `get_settings`，不需要用函数内导入掩盖不存在的循环依赖。

#### 3. 微步 L1：导入与稳定路径

【你写】

```python
from __future__ import annotations

import sys

from loguru import logger

from .settings import ROOT, get_settings

LOG_DIR = ROOT / "data" / "logs"
```

【通俗解释】

- `sys.stderr` 是日志的控制台出口。正常业务输出走 stdout，日志走 stderr，两者不会搅在一起。
- `logger` 是 Loguru 提供的全局日志对象；我们给它安装两个输出规则，这些规则正式名称叫 **sink**。
- `ROOT / "data" / "logs"` 从项目根目录计算。若只写 `Path("data")`，路径会跟着“从哪个目录启动程序”变化，可能把日志写到意外位置。
- `from __future__ import annotations` 会推迟类型注解求值；本项目已经限定 Python 3.11–3.12，`str | None` 本身不依赖它，但统一保留可减少部分前向引用问题。不能把它解释成“老版本 Python 因此支持所有新语法”。

【本步知识点】模块依赖方向、stderr/stdout、`Path` 运算、稳定路径、延迟注解。

【错误写法】代码块必须标记为 `python`；不要把 Python 代码误标为 `ini`、`csharp`、`graphql` 或 `php-template`，否则语法高亮会误导阅读。

【验证】打印 `LOG_DIR`，无论从项目根目录还是其他目录启动，都应指向同一个 `<项目根>/data/logs`。

#### 4. 微步 L2：函数签名与配置优先级

【你写】

```python
def setup_logging(level: str | None = None) -> None:
    console_level = level if level is not None else get_settings().app.log_level
```

【通俗解释】

- 调用者显式传 `level` 时，以调用者为准，方便测试或临时调试。
- 没传时才读 `settings.yaml`，保证生产配置只有一个来源。
- 必须先得到 `console_level`，再交给 `logger.add()`。如果先传入 `level=None`、后面才读取配置，前面的 sink 已经用错值，后赋值不会回头修改它。
- 不用 `level or 配置值`，因为这里真正想判断的是“有没有传”，正式语义是 `is not None`。

【本步知识点】可空类型、默认参数、配置优先级、局部变量、执行顺序。

【验证】分别显式传 `"DEBUG"` 和不传参数，观察 `console_level` 是否来自正确位置。

#### 5. 微步 L3：移除默认 sink

【你写】

```python
    logger.remove()
```

【通俗解释】Loguru 默认已经有一个控制台 sink。如果不移除，再添加自己的控制台 sink，同一条日志会打印两次。多次调用 `setup_logging()` 时先清空，也能避免 sink 越叠越多。

【本步知识点】全局可变状态、初始化幂等性。这里的“幂等”指重复初始化后效果相同，不是付费 API 的请求幂等。

【验证】连续调用两次 `setup_logging()`，再打一条 INFO，控制台仍只能出现一次。

#### 6. 微步 L4：控制台 sink

【你写】

```python
    logger.add(
        sys.stderr,
        level=console_level,
        format=(
            "<green>{time:HH:mm:ss}</green> | "
            "<level>{level: <8}</level> | {message}"
        ),
        colorize=True,
    )
```

【通俗解释】

- `level=console_level` 是过滤门槛；设置 INFO 后，DEBUG 不显示，但 INFO/WARNING/ERROR 显示。
- `format` 只保留操作时最有用的信息，避免终端太吵。
- `colorize=True` 只影响显示，不改变日志等级。

【本步知识点】sink、级别过滤、格式模板、字符串相邻拼接。

【验证】打一条 DEBUG 和一条 INFO；控制台等级为 INFO 时只能看到 INFO。

#### 7. 微步 L5：文件 sink

【你写】

```python
    LOG_DIR.mkdir(parents=True, exist_ok=True)
    logger.add(
        LOG_DIR / "kantoku_{time:YYYY-MM-DD}.log",
        level="DEBUG",
        format=(
            "{time:YYYY-MM-DD HH:mm:ss} | {level: <8} | "
            "{name}:{line} | {message}"
        ),
        rotation="00:00",
        retention="14 days",
        encoding="utf-8",
    )
```

【通俗解释】

- `mkdir(parents=True, exist_ok=True)`：父目录不存在就一起创建，已经存在也不报错。
- 文件固定记录 DEBUG 及以上，保证控制台没显示的调试细节仍可追查。
- `rotation="00:00"`：每天午夜切换新文件，对应 `01` 的“按天滚动”。
- `retention="14 days"`：只保留最近 14 天，对应项目规范，不要自行改成 7 天。
- `encoding="utf-8"`：在 Windows 上明确保证中文日志编码。

【本步知识点】目录创建、日志轮转、保留策略、UTF-8。

【验证】文件存在；DEBUG 只在文件中，INFO 同时出现在控制台和文件中。

#### 8. 失败路径与安全边界

- 配置中的日志等级非法：应让 Loguru/Pydantic 明确报错，不静默改成 INFO。
- 日志目录无法创建：初始化失败并暴露原始原因，不能假装已经记录。
- 日志内容包含密钥、完整 prompt、客户剧本：这是安全事故。只记录长度、摘要、哈希、任务 ID 和错误类型。
- 函数内导入只能推迟导入时机，不能“完美解决”真正的循环依赖；正确办法是让模块依赖保持单向。

### 2.4 `core/llm.py` LLM 客户端

#### 🎯 有什么用
**所有模型调用的唯一出口。** 超时、重试、降级、记 trace 全在这里。
别处一律不许直接 `OpenAI(...)` —— 否则换供应商要改 N 处，trace 也会漏。

**知识 3 分钟**

- OpenAI SDK 的 `OpenAI(base_url=..., api_key=...)` 能接任何 OpenAI 兼容端点（豆包 / 智谱 / 混元都是）
- `chat.completions.create()` 返回 3 层壳：`response.choices[0].message`
- **这次要返回 `message` 对象而不是 `.content`** —— 因为 W2 要读 `message.tool_calls`
- SDK 本身带重试；本项目创建客户端时设 `max_retries=0`，只保留项目自己的重试，避免两层重试叠加
- 只重试连接/超时、408、409、429、5xx；鉴权和参数错误立即失败，避免无意义等待

**契约**

```python
def chat(
    messages: Sequence[ChatCompletionMessageParam],
    *,
    model: str | None = None,         # 默认取 settings.llm.model_chat
    temperature: float | None = None,  # 默认取 settings.llm.temperature
    response_format: ResponseFormat | None = None,
    tools: Sequence[ChatCompletionToolUnionParam] | None = None,
    timeout_s: float | None = None,
) -> ChatCompletionMessage:           # 返回完整 message，保留 tool_calls
    """一次 LLM 调用：超时重试 → 失败转 LLMError → 返回 message。"""
```

**分步 + 自检**

| 步 | 做什么 | 自检方法 |
|---|---|---|
| 1 | `_build_client()`：从 settings 取 URL/key/timeout，并设 `max_retries=0` | mock `OpenAI`，断言四个构造参数；此时不联网 |
| 2 | `_request_once()`：组装 model/messages/temperature/max_tokens，可选加入 tools/response_format | 假响应返回 `choices[0].message`，并保留 `tool_calls` 类型 |
| 3 | `_is_retryable()`：只认连接/超时、408/409/429/5xx | 401 不重试；连接异常可重试 |
| 4 | `_request_with_retry()`：最多初次 + `retry` 次，重试前按 2s/4s 递增等待 | mock 前两次失败、第三次成功，断言调用 3 次和 sleep(2)/sleep(4) |
| 5 | `chat()` 统一异常：不可恢复错误转 `LLMError(... ) from e`，`ConfigError` 原样保留 | 401 得到 `LLMError` 且 cause 是原异常；缺 key 仍是 `ConfigError` |
| 6 | 预留 trace 钩子，下一步记录延迟/token/供应商，不记录完整 prompt | 代码中保留明确 TODO，下一模块替换为真实调用 |
| 7 | 主模型可恢复失败重试耗尽或 404 → 备用供应商；401/403/400 不降级 | 用 mock 404 验证备用模型成功，不使用不存在模型做真实付费测试 |

**掉坑提示**

- 密钥环境变量完全由 `config/settings.yaml` 指定；当前主力是 `DEEPSEEK_API_KEY`，`ARK_API_KEY` 仅保留为可选备用，缺少当前选中的 key 会直接 `ConfigError`（这正是我们设计的保护）
- `base_url` 末尾带不带 `/v1`？**以控制台给的为准**，错了会 404
- OpenAI-compatible 供应商是否支持 `response_format={"type": "json_object"}` 要以当前模型文档为准，**W2 更推荐用 tools**，json_object 只是兜底
- 返回的 message 里 `tool_calls` 可能是 `None`，W2 判断时要用 `if not msg.tool_calls`
- `raise LLMError(...) from e` 会保留原异常作为 cause；开发环境仍可看到异常链，CLI 负责只向用户显示友好消息
- 自动化测试必须 mock 网络，不能靠拔网线、错误 key 或不存在模型；真实调用只保留一次手工集成验收

**过关自测（三问）**
1. 为什么这次返回 `message` 而不是 `message.content`？
2. 超时和重试的值从哪来？
3. 主力模型挂了会发生什么？

### 2.5 `core/tracing.py` 埋点

#### 🎯 有什么用
**W8 的成本/成功率/延迟报告全靠查这张表。** 等到 W8 再补，前面的数据已经永远丢了
——这是全项目最容易烂尾的隐性依赖（`03` §9 风险 R8）。

**契约**

```python
@dataclass(frozen=True, slots=True)
class Trace:
    ts: str
    kind: str
    model: str | None
    in_tokens: int
    out_tokens: int
    latency_ms: int
    cost_fen: int | None
    ok: bool
    shot_no: int | None
    error: str | None
    usage_reported: bool | None = None

def init_trace_table() -> None: ...                 # 路径来自 get_settings，建表幂等
def write_trace(trace: Trace) -> None: ...          # 参数化 SQL 落一条
def recent_traces(limit: int = 50) -> list[Trace]: ...
```

`cost_fen` 使用整数“分”，未知时为 `None`；真正的财务账以 W4 ledger 为准。数据库路径只从
`get_settings().storage.sqlite_path` 读取，相对路径解析到项目根目录，避免启动目录改变后写错库。

R2 补充：`usage_reported=True` 才能按已报告用量解释 token（包括真实 0）；`False` 表示用量未知，整数列的 0 只是兼容占位；`None` 表示历史记录/调用方未标记，不擅自推断。旧库通过 `ALTER TABLE ... ADD COLUMN` 加列，不删除、不重写历史数据。SQL 汇总必须同时给出未知用量条数，不能把未知当免费。

新 LLM 记录 `kind=llm.chat.attempt`，每次重试各记一条；旧 `llm.chat` 粒度不同，报告时分组处理。一次成功无重试仍只有一条；两次超时后成功应为两条失败加一条成功。该成功率是请求尝试成功率，不是用户任务完成率或镜头可用率。

**分步 + 自检**

| 步 | 做什么 | 自检 |
|---|---|---|
| 1 | `Trace`：不可变数据对象 + `__post_init__` 约束 | 成功必须 `error=None`；失败必须有错误摘要；负数被拒绝 |
| 2 | `_database_path` / `_connection`：配置路径、提交、回滚、关闭 | 临时目录中自动建父目录，异常转 `TracingError` |
| 3 | `init_trace_table`：`CREATE TABLE IF NOT EXISTS` | 跑两次不报错，并查 `sqlite_master` 确认表存在 |
| 4 | `write_trace`：参数化 SQL 插入，写前确保表存在 | 含单引号的错误摘要仍能原样写入 |
| 5 | `recent_traces`：明确字段、`ORDER BY ts DESC, id DESC`、参数化 LIMIT | 空库返回空列表；三条取两条且最新在前 |
| 6 | `core/llm.py`：用 `perf_counter` 计时，读取 usage；成功/失败都落 trace | mock 成功记 token；401 记失败；404 降级留下失败+成功两条 |

**掉坑提示**

- 建表要用 `IF NOT EXISTS`；它只能防止重复建表报错，不能替代未来的数据库迁移
- `with sqlite3.connect(...)` 主要管理事务，不等于可以忽略关闭；统一连接函数必须 commit/rollback/close
- SQL 值全部用 `?` 参数传入，不用 f-string 拼接；表名和字段名则不能用参数占位
- `shot_no` 现在是 `None`（W2 才有镜号），字段先留着
- **失败的调用也要记**（`ok=False`），否则成功率永远算出来是 100%
- tracing 自身失败不能覆盖已经成功的 LLM 结果，也不能替换原始 LLM 异常；LLM 边界只记安全错误日志

**过关自测**：
1. `ok=False` 的调用为什么要记？不记会怎样？
2. 为什么耗时使用 `perf_counter()`，事件时间使用带 UTC 时区的 `datetime`？
3. 为什么 trace 的 `cost_fen` 不是最终财务真相？
4. 如果需求改成“按模型统计成功率”，你会查询哪些字段，分母包含什么？

### 2.6 `schemas/storyboard.py` 数据契约

#### 🎯 有什么用
Pydantic 在这里三个用途：① 校验 LLM 返回的 JSON ② `model_dump_json()` 当 schema 样例给 LLM 看 ③ 落库前的统一结构。
**字段名必须和 `03` §2 Step 1 的样例一致**，否则后面到处写转换代码。

**契约（字段不许改）**

```python
class Shot(BaseModel):
    shot_no: int
    desc: str
    dialogue: str = ""
    camera: str
    duration_s: int
    characters: list[str]

class Storyboard(BaseModel):
    episode: str
    shots: list[Shot]

def parse_storyboard(raw: str) -> Storyboard: ...   # 失败抛 SchemaError 且带原文
```

**分步 + 自检**

| 步 | 做什么 | 自检 |
|---|---|---|
| 1 | 写 `Shot` / `Storyboard`，字段与上面完全一致 | 造一个合法 JSON 能解析 |
| 2 | `parse_storyboard`：捕获 `ValidationError` 转 `SchemaError` | 传 `{"bad": 1}` → `.raw` 保留 JSON，异常显示不包含原文 |
| 3 | 造 `EXAMPLE_SHOT_JSON`（`model_dump_json(indent=2)` 的产物） | 打印出来能直接塞进 prompt |
| 4 | 单测：成功 + 失败各一个 | `pytest` 2 passed |

**掉坑提示**

- `model_validate_json()` 是 v2 入口，别用 v1 的 `parse_raw`
- 原始返回保留在 `SchemaError.raw` 中；不得把敏感剧本直接输出到日志。定位字段使用 `detail` 中的路径和错误类别。
- `model_dump_json()` 是实例样例，`model_json_schema()` 才是 JSON Schema，两者不要混淆。
- 当前契约拒绝数字字符串、布尔镜号、空白描述、非正整数时长、额外字段和不连续镜号；空人物列表允许表示空镜。不自动修补 JSON 或删除 Markdown 围栏，修复策略留给 W2。

### 2.7 `shells/cli.py` 命令行外壳

#### 🎯 有什么用

| 4 | `db/schema.sql` | `shot` 表（episode, shot_no, desc, dialogue, camera, duration_s, characters_json） |
| 5 | `evals/storyboard.jsonl` + `scripts/run_eval.py` | ≥10 条 → 第一份报告 |

```python
# agent/loop.py 骨架 —— 不许看资料，闭卷写，写完再对照视频
def run(user_msg: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": user_msg}]
    for step in range(max_steps):
        msg = chat(messages, tools=registry.to_json_schema())
        if not msg.tool_calls:                     # 没有工具调用 = 说人话 = 结束
            return msg.content
        for call in msg.tool_calls:                # 逐个执行工具
            fn = registry.get(call.function.name)
            args = json.loads(call.function.arguments)
            result = fn(**args)                    # ← Pydantic 校验在这里生效
            messages.append({"role": "tool", "tool_call_id": call.id,
                             "content": json.dumps(result, ensure_ascii=False)})
    raise LLMError("超出最大步数，可能陷入循环")
```

**工具注册表契约**

```python
TOOLS: dict[str, Callable] = {}
def register(name: str): ...              # 装饰器
def to_json_schema() -> list[dict]: ...   # 生成 OpenAI tools 参数
def get(name: str) -> Callable: ...
```

**坑**：JSON Schema 的 `parameters` 要手写（先不引自动生成库，先手写懂原理）；
`role="tool"` 消息必须带 `tool_call_id`，否则 API 报错。

**评测集契约**：每行 `{"id","input","expect","rubric"}`；`run_eval.py` 输出通过率。

### ✅ 验收 / 🛑 止损

- **验收**：300 字剧本 → 20 镜分镜表，字段完整率 100%；解析有 mock 单测；评测报告归档。
- **🛑 止损**：Function Calling 卡 >2 天 → 回去重看卢菁博士那两章，**不许绕过**。这条绕过去后面全垮。
